# v0.4.0 — After 0.3.0

_Released 2026-10-22._

## What shipped

### FEAT-216 — A release's notes can be read and edited from the release

A release's notes are visible and editable from the release itself, in the CLI and on the Releases page, without switching branches or making a separate item

- THE SYSTEM SHALL show a release's notes as they are on its release branch, saying where they are, without checking that branch out
- WHEN a release's notes are edited before it is cut, THE SYSTEM SHALL commit them onto its release branch in one commit without checking it out, re-apply the notes listings, and refuse once the release has shipped
- THE SYSTEM SHALL let the notes be shown and saved with kanbanr release notes <V>, from a file or an editor
- THE SYSTEM SHALL show a release's notes on the Releases page and, on a write-enabled monitor before the cut, let them be edited and saved

### FEAT-217 — An item's code says what kind of work it is

An item's code names the kind of work it is (FTR, DEF, MNT, DOC, SPK, set per project) so a defect, a chore or a docs change is told from a feature at a glance, with a counter per prefix; existing FEAT- codes are kept and a later kind change never renames

- WHEN an item is created without an explicit code and the project's codes give its kind a prefix, THE SYSTEM SHALL code it <PREFIX>-<n>, where n is one more than the highest number among the project's items with that prefix, zero-padded to 3
- WHERE a project sets no codes, THE SYSTEM SHALL code every new item FEAT-<n> as before
- WHEN an item has no kind, THE SYSTEM SHALL use the feature entry; WHEN its kind has no entry, THE SYSTEM SHALL use the default prefix, or FEAT when that is absent
- WHEN an item's kind changes, THE SYSTEM SHALL keep its code
- WHEN config codes would set a prefix that is not 2-6 uppercase letters, is reserved (MS, ADR, SC, SP, TL), or is used by a milestone, or a blank or duplicate kind, THE SYSTEM SHALL refuse it naming the entry and leave the config unchanged
- WHEN a batch creates several items, THE SYSTEM SHALL number each by its own prefix in bundle order, and ref aliases SHALL resolve to the assigned codes
- THE SYSTEM SHALL treat a prose token as an item reference only when its prefix is configured or used by an existing item, so SHA-256, RFC-3339, ISO-9001 and UTF-8 are not references; the monitor SHALL agree
- WHEN start runs on a kind-coded defect, THE SYSTEM SHALL branch fix/DEF-001-<slug>, commit SHALL fill Refs: kanbanr:DEF-001, and the hooks, git doctor and why SHALL resolve it
- WHILE codes is unset, THE SYSTEM SHALL load, reference and allocate around existing kind-coded items
- WHEN another config write happens, THE SYSTEM SHALL keep codes unchanged
- WHEN the config's codes are invalid, THE SYSTEM SHALL refuse code allocation naming the problem, and doctor SHALL report it as an error
- WHEN kanbanr config codes runs, THE SYSTEM SHALL show each kind's prefix, the default and the next code per prefix; --set, --unset, --default and --clear SHALL change them

### FEAT-218 — make ci's board check trips on an agent's scoped progress writes

make ci's board check lets through an agent's own progress records made under an active scope, for the person running the release gate, so that a sub-agent working meanwhile does not fail the gate

- WHEN the real board gains commits during make ci, THE SYSTEM SHALL also pass the board check for a commit that carries an Agent-Scope trailer naming a build scope active at the commit's time, updates a task or a test of that scope's item, and touches only that item's file, the activity, the events and the board index, and report each such commit by its scope
- IF a commit made during make ci names a scope that is unknown, revoked or expired at its time, is a design scope, touches another item or any other file, or is not a task or test update, THEN THE SYSTEM SHALL fail the board check as before
