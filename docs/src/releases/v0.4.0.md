# kanbanr 0.4.0 — codes that say what kind of work, and notes edited from the release

*Released 22 October 2026.*

An item's code can now tell you what kind of work it is before you open it, and a release's notes
can be read and edited where the release is, without switching branches or opening an item to do
it.

No board migration is needed: 0.4.0 reads the schema-5 boards 0.3.0 left.

## What's new

- **Codes that say what kind of work an item is.** Map kinds to prefixes once, and each new item
  takes its kind's prefix, with a counter per prefix:
  `kanbanr config codes --set feature=FTR,defect=DEF,bug=DEF,chore=MNT,docs=DOC,spike=SPK`. A new
  defect is then `DEF-001`, a chore `MNT-001`, a feature `FTR-001`.
  - Pass `--kind` at `feature add`, or `kind` in a batch.
  - `kanbanr config codes` on its own shows each kind's prefix, the default and the next code for
    each prefix. `--unset`, `--default` and `--clear` change them.
  - Existing codes are kept, and changing an item's kind never renames it.
  - Branches, commit trailers, the hooks, `git doctor` and `kanbanr why` all understand the new
    codes: `kanbanr start DEF-001` makes `fix/DEF-001-…`.
  - Only this board's own prefixes count as item references, so `SHA-256` or `RFC-3339` in a spec
    is never taken for an item, in the monitor or in `doctor`.
  - A project that sets nothing keeps `FEAT-` for everything, as before.
- **A release's notes, read and edited from the release.** The notes a release prepares live on
  `release/<V>`, not in your checkout. Now you can reach them from the release itself.
  - `kanbanr release notes v0.4.0` shows them and where they are
    (`release/v0.4.0 @ 8c22bb1: docs/src/releases/v0.4.0.md`).
  - `--edit` opens them in your editor, and `--file F` saves a file's text. Either way the change
    is one commit onto the release branch, with nothing checked out.
  - The Releases page has a **Release notes** section on each release with a branch, with **Edit
    notes** and **Save** on a write-enabled monitor.
  - Notes saved after main has moved to the release move main with them, and say to push main
    again before the cut. If main has commits past the release, nothing is saved.
  - Once the release is cut, its notes read as shipped and are no longer edited.
  - No separate item is needed to change a candidate's notes.

## What's fixed

- **`make ci` no longer fails because a sub-agent was at work.** Its check that the real board did
  not move during the run now lets through a build agent's task and test updates made under an
  active scope on its own item, and the scopes you issue, claim or revoke, as it already did your
  approvals and sign-offs. It lists each one by its scope. Anything else still fails the check.

## Upgrade notes

1. Update with `kanbanr self-update` (macOS, Linux) or by rerunning the installer (Windows).
2. Restart `kanbanr serve`.
3. If you want kind codes, set them with `kanbanr config codes --set …` in each project.

Boards need nothing.
