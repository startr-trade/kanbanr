# v0.6.0

_Released 2026-11-13._

## What shipped

### DEF-014 — doctor says a workflow was edited when only its cadence changed

Choosing a cadence or the git model is not read as editing the process, for anyone who applies a process and then turns sprints on, so that `doctor` warns only about real edits to stages, moves or gates and the warning keeps its meaning

- WHEN a project applied from a process that declares no cadence (default, TOGAF) turns on sprints, releases, release stages or the git model, THE SYSTEM SHALL report its workflow as unedited by `doctor` and `process drift`
- WHEN a project's stages, moves or gates differ from the process it was applied from, THE SYSTEM SHALL report its workflow as edited whatever its cadence

### DEF-015 — A scope's brief allows temporary boards, and the scope refuses them

A guard that lets an agent run kanbanr and git on a temporary board, and a brief that says exactly how, for the coordinator who hands work to scoped agents, so that walking a process through on a throwaway board is not refused by the scope that told the agent to do it

- WHEN an agent's command names a data dir (--data-dir or KANBANR_DATA_DIR) that is a temporary board, a folder under the system temporary directory that holds no agent scope, THE SYSTEM SHALL let the command through, and SHALL let KANBANR_PROJECT and --project name any project on that board
- IF an agent's command names a data dir that is not a temporary board (the real board, any folder outside the temporary directory, a folder inside it that holds an agent scope, or a path the guard cannot resolve), or names KANBANR_PROJECT with no temporary data dir, THEN THE SYSTEM SHALL refuse it before it runs and say what a temporary board is and the form to use
- WHEN an agent changes folder before kanbanr or git, or points git at a folder, THE SYSTEM SHALL allow its worktree and any folder under the temporary directory, resolving a leading $TMPDIR or ${TMPDIR}, and SHALL name both places in the refusal for any other folder
- WHEN the brief is printed, THE SYSTEM SHALL state in its Tests row what a temporary board is and the form to name one, from the same rule the guard uses
- THE SYSTEM SHALL decide whether a folder is a temporary board in one function of the core, used by the guard, the brief and the board-governing check

### DEF-018 — An item can't be taken out of a sprint, and a batch says it did

Take one item out of a sprint, and have a batch refuse a field it does not apply, for anyone replanning a sprint so that the board never says a change happened when it did not

- WHEN someone names items in `sprint unplan`, THE SYSTEM SHALL clear each item's sprint, leave every other item and the sprint's own record alone, and say which items left which sprint
- IF an item named in `sprint unplan` is in no sprint, THEN THE SYSTEM SHALL say so by name instead of reporting it removed
- IF an item named in `sprint unplan` is in a closed sprint, or does not exist, THEN THE SYSTEM SHALL refuse the whole command, name the item and change nothing
- WHEN sprints are off for the project, THE SYSTEM SHALL refuse `sprint unplan` as it refuses `sprint plan`
- IF a batch operation carries a field it does not accept, THEN THE SYSTEM SHALL refuse the whole batch, name the operation by position and kind and the field, and write nothing, in a dry run as in a real one
- WHEN a batch is refused for the `sprint` field, THE SYSTEM SHALL say where sprint membership is changed (`kanbanr sprint plan` and `kanbanr sprint unplan`)
- WHEN a batch uses only the fields its operations accept, including every shape the skill, the book, the evidence capture and the mirror send, THE SYSTEM SHALL apply it exactly as before

### DEF-019 — An item shows as released before its release is cut

An item planned into a release that has not been cut stays where it is, however its last task or sign-off arrives, for the developer reading the board so that Operations ("Released and running") is never shown before anything has shipped

- WHEN a sign-off is recorded on an item whose tasks are all done and that is planned into a release which has not been cut, THE SYSTEM SHALL leave the item in its status, in every process, and report that it waits for the cut of that release
- WHEN the last open task of an item planned into a release that has not been cut is completed, singly or in a batch, THE SYSTEM SHALL leave the item in its status and report that it waits for the cut
- WHEN a release is cut, THE SYSTEM SHALL move each planned item whose work is done and whose end gate holds to its end status, including an item that waited for the cut
- WHERE a project has releases switched off, or an item is planned into no release or into a release already cut, THE SYSTEM SHALL finish the item on its last task or sign-off as before
- IF a person moves an item planned into a release that has not been cut to an end status, by move, finish, a batch or the monitor, and gives no reason, THEN THE SYSTEM SHALL refuse and say how to proceed; WHEN a reason is given, THE SYSTEM SHALL make the move and keep the reason on the item
- WHEN a release is cut, THE SYSTEM SHALL move its planned items to their end status without asking for a reason
- WHERE the TOGAF process is used, THE SYSTEM SHALL offer no move from Implementation straight to Operations, so that an item passes Migration, where its branch is merged and its docs sign-off is asked
- WHEN an item is held for the cut, THE SYSTEM SHALL name the release and the end status in the held reason shown by the CLI after `task` and `signoff`, in the same words every surface uses
- THE SYSTEM SHALL describe in the TOGAF, agile and Scrum guides, the processes page and the skill that a sign-off or the last task leaves a planned item in place and that the cut moves it to its end status

### DEF-020 — The monitor's stage counts leave out sign-offs

A board card whose next-stage counts match `kanbanr check`, and that names what is next and who it waits on, for the person reading the board, so that the monitor is never read as wrong

- WHEN a board card names what an item's next stage needs, THE SYSTEM SHALL count every gap `kanbanr check` lists for that stage, sign-offs included
- WHEN a card names what is next, THE SYSTEM SHALL speak only of the stage the item reaches next in the workflow's order, the one the Review page asks sign-offs for, and not of stages it could skip to
- WHEN a card names what is next, THE SYSTEM SHALL say whether it waits on the user (a sign-off or an approval) or on Claude (everything else), and SHALL NOT say it waits for a sign-off while other requirements of that stage are unmet
- WHEN readiness is read by a client written for the earlier answer, THE SYSTEM SHALL still return `missing`, `signoffs`, `tasks_open` and `ends` with their earlier meaning, adding fields only
- WHEN the user opens the board for an item at Implementation with unmet requirements and a sign-off due at Migration, THE SYSTEM SHALL show the same count as `kanbanr check` for Migration and nothing for Operations

### DEF-021 — doctor warns about what a stage doesn't ask for yet

A doctor that warns only about what an item's current stage asks, and counts separately what later stages will ask, for the person running a healthy project, so that a warning always means something to fix now

- WHEN doctor judges a live item in a project that declares its gates, THE SYSTEM SHALL warn only about what the gate of the item's current status requires, and what that gate warns about
- WHEN doctor judges a live item, THE SYSTEM SHALL NOT warn about what only a later stage asks, such as Who and Why for an item at Vision
- WHEN items are waiting for what a later stage asks, THE SYSTEM SHALL report separately, per project and stage, how many items lack how many things at the stage each reaches next, as counts that are not warnings and do not change doctor's exit status
- WHEN an item met its current stage's gate and later stopped meeting it, such as an edit that removed a requirement or a doc declared for a gate asking docs_updated, THE SYSTEM SHALL still warn
- WHEN a client reads the doctor report from an earlier release, THE SYSTEM SHALL return the same `issues` fields with the same meaning, and add the counts as a new field that is omitted when empty
- WHEN doctor is run from the command line, THE SYSTEM SHALL print the counts after the warnings in one line per stage, naming `kanbanr check` as the way to see them

### DEF-022 — The Review page slows down as a board grows

A Review page whose request opens the board's repository once and finds each item's baseline once, for the maintainer whose board keeps growing, so that the page, `kanbanr check` and `doctor` stay fast on a board of thousands of commits

- WHEN the docs_updated check judges the docs an item declares, THE SYSTEM SHALL give the same answer for each doc as judging it alone against the newest commit at or before the time the item entered its stage
- WHEN one readiness evaluation judges any number of items and declared docs, THE SYSTEM SHALL open the board's repository at most once and walk its history at most once
- WHEN a board has no item that declares docs, or no gate asks for docs_updated, THE SYSTEM SHALL NOT open the repository or walk its history
- WHEN the review queue is requested on a generated board of 2,500 commits, 70 items naming docs and 470 doc references, THE SYSTEM SHALL answer in at most the budget recorded in this item's measurement, which is set from the 'before' measure at build time
- WHEN the monitor receives several board changes in quick succession, THE SYSTEM SHALL refetch the review queue once after they settle, not once per change
- WHEN check, doctor, the review queue and board readiness evaluate docs_updated, THE SYSTEM SHALL use the same check, so that they cannot give different answers

### DEF-023 — A scope issued with --worktree tells its agent to claim it, and the claim is refused

A brief that tells an agent only what it still has to do, for the coordinator who issues a scope with --worktree, so that the agent is never told to run a claim that is refused

- WHEN the brief is made for a scope that is already bound to a worktree, THE SYSTEM SHALL omit the claim command and say which worktree the scope is bound to and that nothing needs claiming
- WHEN the brief is made for a scope bound to no worktree, THE SYSTEM SHALL print the claim command as it does now
- WHEN a build scope is already bound, THE SYSTEM SHALL name the branch the worktree is on in the brief, so the agent does not switch it

### DEF-025 — A crash while kanbanr writes can leave a board file half-written

Every board file written whole or not at all, for anyone whose board a crash, a kill or a full disk interrupts, so that a half-written file never stops kanbanr reading the board or ends up committed

- WHEN kanbanr writes a board file, THE SYSTEM SHALL write the new content to a temporary file in the same folder and rename it over the old file, so that the path holds the whole old content or the whole new content at every moment
- WHEN a write fails or is stopped before the rename, THE SYSTEM SHALL leave the old file unchanged, remove its temporary file when it can, and report the error
- WHEN the store saves an item, its spec, a document, a restored document, or any other board file, THE SYSTEM SHALL save it through the atomic write
- THE SYSTEM SHALL have no write path into a board, or into a file kanbanr edits beside it, that does not go through the atomic write, except those the guard test lists with a reason
- WHEN the atomic write replaces a file, THE SYSTEM SHALL keep the old file's permissions and, when the path is a symbolic link, replace the file it points to and keep the link
- THE SYSTEM SHALL keep a leftover temporary file out of the board's reads and out of its commits
- WHEN doctor finds a temporary file of the atomic write older than an hour in a board, THE SYSTEM SHALL report it as a warning that says it is left from an interrupted write and is safe to delete, and SHALL NOT delete or rewrite anything

### DEF-026 — The monitor takes writes on a non-local address without saying so

A monitor that takes writes refusing to start on an address other machines can reach unless the person accepts that explicitly, and accepting an https:// origin only from a proxy the person names, for the person who decides on the monitor, so that exposing decisions to a network is never an accident or a default

- WHEN the monitor is started with writes on and a bind address that is not a loopback address, and the person has not accepted that, THE SYSTEM SHALL refuse to start before it binds or watches anything, and say which address, why it is unsafe, and the two ways to accept it
- WHEN the monitor is started with writes on and a non-loopback bind, and the person passed --allow-remote-writes to serve or set KANBANR_ALLOW_REMOTE_WRITES, THE SYSTEM SHALL start and print a warning that names the address and says that anyone who can reach it can take decisions
- WHEN the bind address is 127.0.0.0/8, ::1 or localhost, THE SYSTEM SHALL start as before without any acceptance
- WHEN the monitor is started without writes, THE SYSTEM SHALL start on any bind address as before
- WHEN kanbanr review --ui starts the monitor and KANBANR_BIND is not a loopback address, THE SYSTEM SHALL refuse in the same way
- WHEN writes are on and the bind address or KANBANR_ALLOW_REMOTE_WRITES cannot be read, THE SYSTEM SHALL refuse to start and say what was wrong
- WHEN a write carries the monitor's token, a Host the monitor answers for, and an Origin that the person named in KANBANR_ALLOWED_ORIGINS, THE SYSTEM SHALL accept it, whether that origin is http or https
- WHEN a write carries an Origin that is neither the monitor's own http origin nor one the person named, THE SYSTEM SHALL refuse it with 403 and change nothing, including an https origin whose host the person allowed only in KANBANR_ALLOWED_HOSTS
- WHEN KANBANR_ALLOWED_ORIGINS holds an entry that is not an http or https origin (scheme, host, optional port, nothing else), THE SYSTEM SHALL refuse to start and name the entry
- THE SYSTEM SHALL describe in SECURITY.md and the monitor docs the non-loopback refusal, the acceptance, and how to take writes through a TLS proxy with KANBANR_ALLOWED_ORIGINS

### DEF-027 — The coordinator's shell is trapped once it enters an agent's worktree

A scope that binds the agent it was issued to and not whoever stands in its folder, for the person who works a project through Claude, so that a coordinator's shell is never refused by an agent's scope, a revoke frees it at once, and the test-capture hook keeps recording

- WHEN a kanbanr command or git hook runs outside a Claude Code session, THE SYSTEM SHALL apply no agent scope to it, wherever its working folder is
- WHEN a Claude Code hook call carries no agent_id, THE SYSTEM SHALL treat it as the coordinator's and apply no agent scope to it, wherever its working folder is
- WHEN a scope is revoked or its expiry passes, THE SYSTEM SHALL refuse every further call of its agent at once, through the hooks, and SHALL NOT refuse a command from a shell that is not that agent's
- WHEN the coordinator runs a kanbanr or git command while its shell stands in an agent's worktree, THE SYSTEM SHALL refuse it before it runs, say the shell is in that worktree, and name the way out (`cd` to the project folder, and `git -C <path>` to look inside)
- WHEN the coordinator's command would leave its shell standing in an agent's worktree (a top-level `cd` or `pushd` into one), THE SYSTEM SHALL refuse it and name `git -C <path>`, a subshell `(cd <path> && …)` or the tool's own directory flag instead, and SHALL let the same forms through when they stay in a subshell
- WHEN the capture hook runs, THE SYSTEM SHALL find the board and project from the project folder the hook is registered for, not from the shell's working folder, and SHALL record tracked tests the coordinator's run showed whatever folder it ran in, and only the agent's own item's tests for an agent
- WHEN a refusal comes from an agent scope or from an agent worktree with no scope, THE SYSTEM SHALL say, besides what the agent does, what the coordinator or the person does to get out of it
- WHEN a scope is issued, THE SYSTEM SHALL refuse it unless the Claude Code hooks that identify the caller (the Bash and Write guards, the capture hook) are registered for the project or the user, and name `kanbanr hooks install`
- WHEN the skill and the process guides explain handing work to sub-agents, THE SYSTEM SHALL tell the coordinator to stay in the project folder, to use `git -C`, `make -C`, `npm --prefix` or a subshell for anything inside an agent's worktree, and what to do if its shell is already there

### DEF-028 — A decision does not record where it was taken

Every verdict on the board recording where it was taken (monitor, conversation, terminal), and a repeat of the same verdict on the same text recording nothing, for the person who decides and the one who reviews what was decided, so that a double decision is seen, can be audited, and is not counted twice

- WHEN an approval, ratification or withdrawal of an approval, or a sign-off or its withdrawal, is recorded, THE SYSTEM SHALL record its origin (monitor, conversation or terminal) on the record, with who gave it and when
- WHEN a decision is accepted or rejected, THE SYSTEM SHALL record its origin in the decision's front matter beside who decided and when
- WHEN a release is promoted, a stage after the tag is confirmed, a patch is started from a failed tag, or a release is cut, THE SYSTEM SHALL record who did it, when, and the origin, on the stage change and, for the cut, on the release
- WHEN a verdict arrives at a front end, THE SYSTEM SHALL take its origin from that front end (the monitor's server: monitor; the CLI: conversation when run inside a Claude Code session, else terminal) and SHALL ignore an origin the request itself carries
- WHEN an item, a release or a decision is shown, THE SYSTEM SHALL show the origin of each verdict on it, in the monitor, in `feature show`, `release show` and `adr show`, and in their `--json`, reading a record that has none as origin unknown
- WHEN a board written before origin existed is read, THE SYSTEM SHALL read every verdict on it as origin unknown and SHALL leave its files byte-identical
- IF a verdict is identical to the latest verdict on the same text (the same approval, ratification or sign-off on an item whose definition has not changed since), THEN THE SYSTEM SHALL record nothing, make no activity entry, event or commit, and answer who recorded it first, when and from where
- IF a decision, a promotion, a cut or a withdrawal is asked for a second time and is refused as already done, THEN THE SYSTEM SHALL name in the refusal who recorded the first, when, and from where
- WHEN a verdict is recorded, THE SYSTEM SHALL carry its origin on the activity entry and on the event it produces

### DEF-029 — Shipped items stay in Migration, and new items miss the sprint

A release that refuses to leave behind merged work and a doctor that names finished-in-release items still unfinished and release items outside the running sprint, for the developer cutting a release so that the board says truly what shipped and who is working on what

- WHEN a promotion that enters the stage that tags, or the stage that ships, is planned or made, and an item planned into the release has its code merged but would be carried over because its end gate does not hold, THE SYSTEM SHALL hold the promotion, naming each such item, what it lacks and how to proceed
- WHEN the cut would carry over an item whose work is not done or not merged, THE SYSTEM SHALL carry it with its reason, as before, and SHALL NOT hold the promotion for it
- WHEN doctor finds an item planned into a release that has shipped and not at an end status, THE SYSTEM SHALL warn, naming the item, the release and its date, the item's status and what holds it, and SHALL NOT warn about an item the cut carried into another release
- WHEN doctor finds, while a sprint is running, a live item planned into a release that has not shipped and into no sprint, THE SYSTEM SHALL warn, naming the item, the release, the sprint and the command that plans it in
- WHEN items are planned into a release while a sprint is running, THE SYSTEM SHALL say, in the same reply, which of them are in no sprint and the command that plans them in, and SHALL NOT plan them into the sprint itself
- THE SYSTEM SHALL tell Claude, in the skill and the TOGAF guides, to plan an item into the running sprint when it plans it into a release, and to leave the sign-off that holds a merged item to the person

### DEF-031 — A change to a release past candidate doesn't send it back through the process

A release that goes back to candidate when an item is merged into it past candidate, with the steps from there laid out on the Releases page, for the developer cutting a release so that the commit that is tagged is always one that main and the gate have reached

- WHEN an item is merged into the branch of a release that is at a stage after its first and has not been tagged, THE SYSTEM SHALL return the release to its first stage, recording on the stage change the item, who moved it, when and why, and say so in the reply to the move
- WHEN an item is merged into the branch of a release that is at its first stage, has no stage, or has shipped, or the branch already held the item, THE SYSTEM SHALL change nothing about the release
- IF an item would be merged into the branch of a release that has been tagged and has not shipped, THEN THE SYSTEM SHALL refuse the move before merging or changing anything, naming the tag and the patch release that takes the change
- WHILE a release sent back by an item has not been cut, THE SYSTEM SHALL show in its plan, on the Releases page and in release promote --plan, the item that sent it back and the steps from candidate in order: update the notes, run the gate again, promote to main, push and wait for CI, cut, keeping only the steps this project's stages have
- WHEN a release's notes are read before the cut, THE SYSTEM SHALL list the items planned into the release whose code the notes do not mention, and the Releases page SHALL show that list beside the notes
- WHERE gate_passed is judged for a release tip with no result of its own, THE SYSTEM SHALL count the newest passed result of the same gate recorded for an earlier commit of the release when every path changed since then matches the project's documentation paths, naming that commit, and SHALL NOT count a failed result, or a result across a change to any other path
- WHILE a release was sent back and has not been cut, THE SYSTEM SHALL refuse to enter the stage that tags until main is at the release tip and the tip is on main's remote-tracking branch, and until the gate passed where the project names commit gates, whatever that stage requires
- WHEN a release's notes are saved, THE SYSTEM SHALL move main with them as it does now and SHALL NOT send the release back
- THE SYSTEM SHALL describe in the TOGAF guides and the skill that a merge into a promoted release returns it to candidate and what the person does from there, and that Claude reports it and confirms no stage

### DEF-033 — A sign-off is offered before the work it confirms is done

A docs-folded sign-off that is offered only once the item's documents are built, for the person who signs off, so that the sign-off confirms documents that exist

- WHEN the review queue is built, THE SYSTEM SHALL NOT offer the docs-folded sign-off for an item whose documents are not built, however many board docs the item names
- WHEN docs-folded is asked of an item, THE SYSTEM SHALL count its documents as built only when every board doc it names has changed since it entered its stage, every repository doc its Design lists under Affects docs has changed on its branch against the line it merges into, and every task that writes docs is complete
- WHEN an item names no board docs, lists no repository docs and has no docs task, THE SYSTEM SHALL offer docs-folded once the item has tasks and all are complete, and SHALL say the item changes no documents
- WHILE the documents of an item are not built, THE SYSTEM SHALL show on kanbanr check, the readiness view and the board card each document still unbuilt and why, and SHALL refuse a docs-folded sign-off request for it, naming them
- IF the repository docs cannot be read, because no code repository is attached or the item has no branch in it, THEN THE SYSTEM SHALL hold docs-folded and say which, and SHALL NOT treat the repository docs as built
- WHEN a docs-folded sign-off was given before this check existed, THE SYSTEM SHALL keep it recorded and counted, and SHALL NOT rewrite it when reading
- THE SYSTEM SHALL build the review queue of 70 items, none of which lists a repository doc, in under 1 second on the DEF-022 generated board, with no git process started for them
