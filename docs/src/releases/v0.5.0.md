# kanbanr 0.5.0 — a safer monitor, honest release dates, and a guide for every process

*Released 7 November 2026.*

The monitor now answers only its own page, a release is dated the day it reaches main, and an item
tells you which release shipped it. The book gains a guide for every built-in process, and a long
list of small fixes makes the commands say what is true.

If you run the monitor with writes on, upgrade.

## What's new

- **An item says which release shipped it.** On a project that works in releases, an item's page and
  `kanbanr feature show` now say "Released in v0.4.0", "Planned for v0.5.0, not released yet" or "Not
  in a release", so a Completed item is not mistaken for a released one.
  - Projects that do not work in releases show no such line.
  - The JSON export gains an optional `release_line` field.
- **The Review page lists finished items whose approval lapsed.** A Completed item whose definition
  changed after it was approved now appears in the review queue, after live work and labelled with
  its status, with the Approve button. Re-approving finished work no longer needs a terminal.
  - Items never approved, and items in a no-op status, stay out.
- **`kanbanr release redate`.** If main has already moved when you notice a release carries an old
  date, `kanbanr release redate` dates its notes and changelog heading today, moves main with them if
  main holds the release, and tells you to push again. After the release ships it refuses.
- **Gates tell you when there is no charter.** On a project with no charter, a move a gate would have
  refused still goes through, but it now warns what the gate would have needed and that
  `kanbanr charter set` turns the gates on. A move the gate would have passed says nothing.
- **`kanbanr check` names a manual test nobody ran.** A manual test that is not green is listed under
  its item as `manual test not run: R-4: <name>`, and as `open_manual` in `--json`. It is a note, not a
  gap: readiness and the exit status are unchanged.
- **The retro reads as it means.** `requirements proven by a green test: 56/56` now adds `(1 with a
  test still open)` when a proven requirement also has a test that is not green; `--json` gains
  `evidence.proven_with_open_test`. The two defect lines are worded apart: `added as defect items`
  and `defects recorded with their cause`.
- **`kanbanr why` explains a line not yet committed.** Instead of "Nothing on the board explains this
  code", it says the line is not committed yet and names the item your branch belongs to, or says the
  branch names none.

## What's fixed

- **The monitor answers only its own page and hosts.** It now serves and accepts requests only for its
  own page and the hosts it is bound to. A write needs a token that is made at each start and given
  only to the monitor's own page.
  - A copy of the monitor page hosted on another site can no longer read the board: use the page
    `kanbanr serve` serves.
  - Behind a reverse proxy, name its host in `KANBANR_ALLOWED_HOSTS` (comma-separated `name[:port]`).
    Behind an HTTPS proxy, treat the monitor as for reading.
  - `SECURITY.md` now describes write mode and how it is limited.
- **Release dates and notes.** A release cut later no longer ships the date of its candidate: v0.4.0
  was prepared on 22 October and cut on 1 November, and shipped saying 22 October. The stage that
  moves main now dates the notes and changelog heading today, in one commit, before main moves. If
  main moved already, the cut's plan warns and names the dates. Also, the board's copy of a release's
  notes (`releases/<V>.md`) now holds the notes file that shipped, at the tagged commit, when the
  project configures one, instead of the generated requirements list.
- **JSON output.** `--json` now works on `feature show`, `why` and `board`. They printed text despite
  the flag, and a failed parse of that text is how an item's spec got blanked. Each prints one JSON
  document; `feature show` matches `export --format json`.
- **Specs are not blanked by an empty file.** `--spec-file` on `feature add` and `feature edit`
  refuses a file that is empty or only whitespace, names it, and changes nothing. To clear a spec on
  purpose, pass `--spec ""`.
- **Redefining an item keeps its record.** `kanbanr feature define` from a file with no history used
  to drop the item's approval history and sign-offs. Both are now kept in order, each entry once, and
  read as lapsed if the content changed.
- **`kanbanr start` leaves your checkout alone when the gate refuses.** It asks the gate first and
  makes or switches branches only once the move would pass. A refused start says what is missing.
  `--override` still branches and moves the item.
- **`git doctor` and `doctor`.**
  - `git doctor` no longer calls merged work not integrated when the workflow has no integrate
    stage. Items at or before build, and workflows with an integrate stage, are judged as before.
  - `doctor` no longer reports a shipped release's book links as broken. Unknown items,
    requirements, milestones and goals there, and broken links in every other doc, are still
    reported.
- **Worktrees under `.claude/worktrees` can commit.** A worktree you or a coordinator make there, for
  example to resolve a merge, was refused as if it were an agent's. Now only a worktree named
  `agent-*`, the name Claude Code gives an agent's, is refused without a scope. A scope bound to a
  worktree still holds it whatever it is called.
- **`scripts/ci_local.py --help` no longer starts the whole gate.** `-h` and `--help` print the usage
  and exit 0. Any other argument is named, refused with exit 2, and runs no check. `make ci` is
  unchanged.

## Docs

- **A guide for every built-in process.** The book has a Process guides section covering TOGAF,
  default, scheduled, PDCA, design control, Scrum and agile, and sprints and releases. Each has one
  guide you follow by talking to Claude and deciding on the monitor, and one from the command line.
  They say what surprises people: gates need a charter, an item merged but not yet released carries
  over at a sprint close, and each item needs its `release` sign-off before main. Working with Claude
  links them from each process's row.
- **The stability page matches 0.4.** It no longer says the feature set is frozen: until 1.0 nothing
  is promised and releases may add. It lists `scopes.yaml`, the `codes`, `release_gates` and
  `release_prepare` settings, and the `Agent-Scope:` trailer and pre-push hook, and names agent
  scopes, release stages and kind codes as experimental in 1.0, stable from 1.1.
- **The book and the skill match this release.** The no-charter warning, the date set when main
  moves, `why` on an uncommitted line, `git doctor` with no integrate stage and lapsed approvals on
  finished items are described as they now behave, and the skill tells Claude about them.
- **The extension's README links the getting-started video.** The 2-minute video, linked from a
  thumbnail before the feature list, shows kanbanr working before you install the extension.

## Upgrade notes

1. Update with `kanbanr self-update` (macOS, Linux) or by rerunning the installer (Windows).
2. Restart `kanbanr serve`.
3. If the monitor sits behind a reverse proxy, set `KANBANR_ALLOWED_HOSTS` to the proxy's host.

Boards need nothing.
