# v0.5.0

_Released 2026-11-06._

## What shipped

### DEF-001 — A release cut later ships the date of its candidate

A release's notes and changelog carry the date it reaches main, and a later cut says when they are stale and how to correct them, for the person releasing, so that a release does not ship with the wrong date

- WHEN a release is promoted to the stage that moves main and its notes or changelog heading are dated before today, THE SYSTEM SHALL commit today's date onto the release branch before main moves
- WHEN the cut is planned and the notes or changelog heading are dated before today, THE SYSTEM SHALL warn, naming both dates and the redate command, without refusing the cut
- WHEN kanbanr release redate runs before the cut, THE SYSTEM SHALL commit today's date onto the release branch, move main with it if main holds the release, and say to push again; once shipped it SHALL refuse

### DEF-002 — An empty spec file blanks an item's spec

A spec file with nothing in it is refused instead of saved, for anyone editing an item, so that a failed export cannot erase a spec

- IF a file given to --spec-file is empty or only whitespace, THEN THE SYSTEM SHALL refuse it, naming the file, and change nothing

### DEF-003 — kanbanr check does not name a manual test nobody ran

kanbanr check names each manual test not yet run, without failing the check, for the person finishing an item, so that an unrun check is seen before the item is called done

- WHEN kanbanr check runs on an item with a manual test not green, THE SYSTEM SHALL name that test and its requirement, with the item's readiness and the exit status unchanged

### DEF-004 — Without a charter, gates do nothing and say nothing

A move a gate would have refused says so on a project with no charter, for someone who skipped the charter, so that they learn the gates are not being enforced

- WHEN a move on a project with no charter would have been refused by its gate, THE SYSTEM SHALL allow it and warn what would have been missing and that kanbanr charter set turns the gates on
- WHEN a move on a project with no charter would have passed its gate, THE SYSTEM SHALL say nothing about the charter

### DEF-005 — The board's copy of a release's notes is not what shipped

The board's release document holds the notes that shipped, for anyone reading releases on the board, so that the board and the repository agree

- WHEN a release with a configured notes file is cut, THE SYSTEM SHALL write that file's text at the tagged commit to the board's release document, and generate it only when there is no such file

### DEF-006 — The retro's proven count and defect lines mislead

The retro says how many proven requirements still have a test open, and tells its two defect lines apart, for anyone reading it, so that its numbers mean what they seem to

- WHEN a retro reports proven requirements, THE SYSTEM SHALL also report how many of them still have a test not green
- THE SYSTEM SHALL word the retro so that items added of a defect kind and defects recorded with a cause are told apart

### DEF-007 — kanbanr start leaves you on a new branch when the gate refuses

kanbanr start checks the gate before it makes or switches a branch, for the person starting an item, so that a refused start leaves the checkout as it was

- IF the gate refuses a kanbanr start, THEN THE SYSTEM SHALL say what is missing, make no branch and leave the checkout on the branch it was on
- WHEN a start is given --override, THE SYSTEM SHALL make the branch and move the item as before

### DEF-008 — feature define erases sign-offs and approval history

Redefining an item from a file keeps its sign-offs and approval history, for anyone using feature define, so that a redefinition lapses an agreement instead of erasing the record of who gave it

- WHEN a definition is replaced by one that carries no approval history, THE SYSTEM SHALL keep every earlier approval and withdrawal, in order
- WHEN a definition is replaced by one that carries no sign-offs, THE SYSTEM SHALL keep every earlier sign-off and withdrawal, in order, and read each as lapsed if the content changed
- WHEN the replacing definition already holds some of the earlier approvals or sign-offs, THE SYSTEM SHALL record each entry once and add the ones it lacks
- WHEN feature define is given a file without history, THE SYSTEM SHALL show the item's approval and sign-offs afterwards in feature show --json

### DEF-009 — --json is ignored by feature show and why

Every read command that takes --json prints JSON, for scripts and Claude that parse it, so that a failed parse of text can no longer blank an item's spec

- WHEN feature show runs with --json, THE SYSTEM SHALL print the item as one JSON document, the same as export --format json
- WHEN why runs with --json, THE SYSTEM SHALL print one JSON document with the target, where the reference came from, and for each reference its requirements, goal, purpose, decisions and documents; a target with no reference prints the same document with an empty references list
- WHEN board runs with --json, THE SYSTEM SHALL print the project and, for each state in board order, its items with code, title and task counts
- THE SYSTEM SHALL parse as JSON the output with --json of every read command that takes the flag, except those whose payload is a named format or a document body

### DEF-010 — ci_local.py --help starts the whole gate

A --help flag that prints usage, and a refusal of any argument the script does not know, on scripts/ci_local.py for anyone running the release gate, so that asking for help or mistyping a flag never starts a full make ci

- WHEN the script is given -h or --help, THE SYSTEM SHALL print its usage and exit 0 without running any check, building a tree or reading the board
- IF the script is given any argument other than -h or --help, THEN THE SYSTEM SHALL name the argument, print the usage, exit 2 and run no check
- THE SYSTEM SHALL pass the arguments given to scripts/ci-local.sh through to the script unchanged

### DEF-011 — why says nothing explains an uncommitted line on an item's branch

A line not yet committed is reported as uncommitted, with the item its branch belongs to, for anyone asking `kanbanr why` about work in progress, so that new code is never described as unexplained

- WHEN kanbanr why is given a line that is uncommitted and carries no annotation, on a branch that names an item on the board, THE SYSTEM SHALL say the line is not yet committed and name that item, instead of saying nothing explains it
- WHEN the line is uncommitted and the checkout is not on an item's branch, THE SYSTEM SHALL say the line is not yet committed and that no item is named, and SHALL NOT claim nothing explains it
- WHEN a line is uncommitted but carries an annotation, THE SYSTEM SHALL answer from the annotation as before
- WHEN a line is committed and no commit or annotation names a reference, THE SYSTEM SHALL keep saying it carries no reference

### DEF-012 — git doctor reports merged items as not integrated when no stage holds the integrate role

git doctor leaves alone commits serving an item that has passed its build stage when the workflow has no integrate stage, for anyone running it on such a board, so that a merged item is not reported as not integrated

- WHEN no stage holds the integrate role and an item is at a status after the build stage, THE SYSTEM SHALL NOT report commits on a line serving it as work that is not integrated
- WHEN no stage holds the integrate role and an item is at or before the build stage, THE SYSTEM SHALL still report commits on a line serving it as not integrated
- WHEN a stage holds the integrate role, THE SYSTEM SHALL judge an item integrated only by that role, as before

### DEF-013 — The Review page does not list finished items whose approval lapsed

A Review queue that also lists finished items whose approval lapsed, with the Approve button, for the person who agrees to definitions, so that re-approving finished work needs no terminal

- WHEN the review queue is read, THE SYSTEM SHALL list an item in a finished status, other than a no-op disposition, whose approval has lapsed, marked finished, with its status
- WHEN the review queue is read, THE SYSTEM SHALL keep out a finished item that is currently approved or ratified, one never approved without a recorded bypass, and one in a no-op status
- WHEN the user approves a finished item listed as lapsed on the Review page, THE SYSTEM SHALL record the approval pinned to the definition shown and drop the item from the queue
- WHEN the review queue holds live and finished items, THE SYSTEM SHALL order finished items after live work and before the release question, and label each on the page with its status and a lapsed approval
- THE SYSTEM SHALL decide which finished items the queue lists from one shared rule in graph.rs, so that the queue and any other surface cannot give different answers

### DEF-016 — doctor reports shipped release notes' book links as broken

doctor leaves a shipped release's board document as it shipped and doesn't report its book links as broken, for anyone reading doctor's errors, so that a real broken link isn't lost among false ones

- WHEN doctor checks a board document under releases/, THE SYSTEM SHALL not report its links to documents as broken
- WHEN doctor checks a board document under releases/ that names an item the board does not have, THE SYSTEM SHALL still report it
- WHEN doctor checks a board document outside releases/ with a broken link, THE SYSTEM SHALL still report it as an error

### DEF-017 — A worktree the coordinator makes under .claude/worktrees cannot commit

A worktree a person or coordinator makes under .claude/worktrees commits under the ordinary hooks, while an agent's worktree stays refused without its scope, for anyone keeping worktrees in that folder, so that keeping to that location doesn't block the work

- WHEN a commit is made in a worktree under .claude/worktrees whose name does not start with agent- and which has no scope bound, THE SYSTEM SHALL apply the ordinary hooks and no agent scope refusal
- IF a worktree under .claude/worktrees has a name starting with agent- and no scope bound, THEN THE SYSTEM SHALL refuse its commits and board writes as it does now
- WHILE a scope is bound to a worktree, THE SYSTEM SHALL enforce that scope whatever the worktree's name

### DEF-024 — The monitor accepts requests from other origins

The monitor serves and accepts requests only for its own page and the hosts it is bound to, for the person deciding on it, so that nothing else running in their browser can read the board through it or record a decision

- WHEN a request reaches the monitor with a Host header that names neither a loopback name nor the bound address nor a host the person allowed, THE SYSTEM SHALL refuse it with 403 and change nothing
- WHEN a request carries an Origin other than the monitor's own, THE SYSTEM SHALL answer without any header that lets that origin read the response
- WHEN a write reaches the monitor without the token its own page was given at this start, or with an Origin other than its own, THE SYSTEM SHALL refuse it with 403 and change nothing on the board
- WHEN the monitor's own page writes, THE SYSTEM SHALL accept it as before
- WHEN the monitor starts, THE SYSTEM SHALL make a new random token and give it only to its own page
- THE SYSTEM SHALL describe in SECURITY.md that the monitor can take writes, and how they are limited to its own page

### DOC-002 — The stability page matches what 0.4 actually is

The stability page lists every surface 1.0 would promise and says what holds until then, for anyone relying on kanbanr, so that the promise can be read and checked

- THE SYSTEM SHALL document on the stability page every board file, config setting and commit trailer that 1.0 promises, and what holds before 1.0, as it actually behaves

### DOC-003 — Process guides for the other built-in processes

A guide to each built-in process, by talking to Claude and from the command line, for someone choosing or running that process, so that each process can be followed without reading its gates

- THE SYSTEM SHALL document each built-in process from the command line, with every command and output as seen in that process's own run
- THE SYSTEM SHALL document each built-in process as what the person says to Claude and which monitor page and button each decision uses

### DOC-005 — The extension's README links the getting-started video

The extension's README links the 2-minute getting-started video for people who find the extension on Open VSX, so that they can see kanbanr working before they install it

- THE SYSTEM SHALL show, on the extension's README before its feature list, the getting-started video as a thumbnail linking to https://youtu.be/eBe9Z-OrenE, with a caption that says what the video covers and that installing the extension is covered under Install

### DOC-006 — The book and the skill catch up with 0.5.0

The book and the kanbanr skill describe what 0.5.0 does, for readers and for Claude, so that neither is told an older behaviour on the day it ships

- THE SYSTEM SHALL document, in the book, the no-charter warning, the re-dating at the move to main, why on an uncommitted line, git doctor with no integrate stage, and finished items with a lapsed approval on the Review page, as 0.5.0 behaves
- THE SYSTEM SHALL tell Claude, in the skill, about the no-charter warning, release redate, the process guides, a named open manual test and the Review page's finished items
- WHEN the book is built, THE SYSTEM SHALL build with no broken internal link in the changed pages

### FTR-001 — An item says which release it shipped in

An item's page and feature show say which release shipped it, or that it is not released yet, for anyone reading the item, so that Completed is not mistaken for released

- WHILE a project works in releases, THE SYSTEM SHALL show on the item's page and in feature show that an item was released in <V>, is planned for <V> and not released yet, or is in no release
- WHERE a project does not work in releases, THE SYSTEM SHALL show no release line
