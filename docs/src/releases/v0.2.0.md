# kanbanr 0.2.0 — one method for every process, and a board format that will last

*Released 21 October 2026.*

This release does two things. It makes one way of working the default in every process:

- a build-ready design is agreed before code is written;
- the architecture docs are kept as built;
- references are live links that kanbanr checks;
- the code repository's branches follow your cadence.

And it moves the board to a format meant to last until 1.0 and beyond: a maintained YAML library,
and approvals that no longer depend on how a file happens to be written.

**Every board has to be migrated once.** Run `kanbanr migrate` after updating; see
[Upgrade notes](#upgrade-notes).

## What's new

- **The method, on by default in every built-in process.**
  - An item cannot enter the build stage until its spec has a `## Design` section and someone has
    signed off `design-review`. It cannot finish until the docs it named are updated and someone
    has signed off `docs-folded`.
  - `kanbanr config method` shows which parts are on, and turns any of them off.
  - The skill states the method once, by the role a stage plays (design, build, integrate,
    release), so it reads the same under kanban, Scrum, TOGAF, PDCA or a process of your own.
    Personal instruction files that restate it are no longer needed.
  - See [The method by stage role](../using/the-method.md#the-method-by-stage-role).
- **Living architecture docs.**
  - An item names the board docs its design changes in `affects_docs`. A `docs_updated` gate checks
    that each one was updated before the item moves on.
  - **Coverage rules** keep the cross-cutting views whole. A project can say, for example, that the
    Zachman matrix must reference every item past Design, or that some doc under `architecture/`
    must reference every accepted ADR.
  - kanbanr checks the rules whenever the board changes, a `docs_cover` gate can require them, and
    `kanbanr doctor` lists every gap.
  - See [Living architecture docs](../using/living-docs.md).
- **Live, checked references.** `FEAT-012`, `ADR-0005`, `MS-004` and doc paths in specs and docs
  link to their pages in the monitor, and a reference to something that doesn't exist is reported.
- **The code repository follows your cadence.**
  - `kanbanr git model` shows where items branch from and merge into: main, a sprint branch, or an
    integration line. It also shows where production moves.
  - With the git model on, moving an item into its integrate stage merges its branch.
  - `kanbanr git doctor` reports where the board and the branches disagree.
  - Setup now asks, for every process, whether you work in sprints and releases, and shows the
    resulting model before applying it (`kanbanr git model --sprints on|off --releases on|off`).
- **Releases move through stages.**
  - `kanbanr release promote` takes a release from candidate through test and staging to
    production. Production is the cut: kanbanr tags the code repository and brings main up to the
    release.
  - Patches are their own releases: `kanbanr release add v1.0.1 --patch-of v1.0.0`.
  - The monitor's Releases page offers the promotion and shows what the cut would ship and carry
    over.
- **Stage roles.** A gate can say what its stage is for (`roles: [design]`), so a rule written for
  "the design stage" works in any process.
- **Sign-offs can be withdrawn,** with a reason (`kanbanr signoff … --withdraw`). The monitor
  offers a sign-off only when it would count.
- **Diagrams drawn by Pele, in your theme.**
  - The book and the monitor draw ```` ```mermaid ```` blocks with [Pele](https://pele.run)
    instead of Mermaid.
  - A diagram takes its colours from the theme you read in (each of the book's five, the monitor's
    light and dark) and follows a theme switch without reloading.
  - The book loads one 680 kB script instead of 2.5 MB.
- **Diagrams are checked when they are written.**
  - Writing a spec or doc warns about a diagram Pele would reject, naming the file, diagram, line
    and rule. `kanbanr config diagrams --strict on` refuses the write instead.
  - A `diagrams_valid` gate can require clean diagrams, and `kanbanr doctor` lists every broken one.
  - The Review page keeps Approve disabled until every diagram in the item's spec, and in the docs
    it names, parses. It says what is wrong and links to the source.
  - The doc viewer shows a broken diagram's source with the error under it.
- **A versioned read API.**
  - The daemon's public read routes are version 1 of a documented contract, described in OpenAPI
    3.1 at `GET /api/openapi.json`.
  - A contract test checks every route against it. See [HTTP API](../reference/http-api.md).
- **The monitor as a standalone bundle.** Each release attaches `kanbanr-monitor-v0.2.0.tar.gz`, a
  read-only monitor you can host on any static server and point at a daemon.
- **Every board explains how to view it.** A board's `README.md` walks a reader from nothing to the
  board, and is kept current as projects change. On an existing board, run `kanbanr readme`.
  `kanbanr doctor` reminds you until you do.

## What's changed

- **A maintained YAML library.**
  - Board files are read and written with serde-saphyr, which is maintained and has no `unsafe`
    code. It replaces serde_yaml, whose parser is no longer maintained.
  - Approvals, sign-offs and process records are now pinned to a canonical form of their content.
    Rewriting a file no longer lapses them.
  - This is the one-time migration below; the board's schema is now 5.
- **Board cards say plainly what an item needs next.**
  - The old next-stage pill read like a status. A card now says "In Progress needs 2", "waiting
    for sign-off docs-folded", "ready for In Progress" or "ready to complete". It says nothing while
    the item's tasks are open.
- **One copy of every board rule.**
  - The CLI and the daemon now call the same core functions for writing, git, workflow moves, test
    evidence, the process library and the issue mirror. Behaviour is unchanged.
  - Two small differences:
    - `feature add --found-in` makes one commit instead of two.
    - A few daemon write failures now answer with the same HTTP status a read gets for the same
      error.

## What's fixed

- A sign-off that clears an item's last hold now finishes the item, as ticking the last task does.
- A build that went through a shared compiler cache (sccache) could ship without the monitor or
  the skill. It now always includes them, and a release build without them fails.
- The Workflow page draws its diagram and shows each stage's gates again on projects that use stage
  roles.
- Deleting a project removes its folder for good.
- The board is found from inside a git worktree.

## Security

- `webpki-roots` 1.0.10 and `rustls-webpki` 0.103.16, which close
  [RUSTSEC-2026-0381](https://rustsec.org/advisories/RUSTSEC-2026-0381) and
  [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382). The trust store behind
  self-update and the release check could accept certificates chained through distrusted emSign
  intermediates.
- rustls 0.23.46 ([RUSTSEC-2026-0346](https://rustsec.org/advisories/RUSTSEC-2026-0346),
  [RUSTSEC-2026-0348](https://rustsec.org/advisories/RUSTSEC-2026-0348)).
- No unmaintained YAML parser, and no advisory exception left in the supply-chain policy.

## Upgrade notes

1. Update with `kanbanr self-update` (macOS, Linux) or by rerunning the installer (Windows). This
   also updates the Claude Code skill and the VS Code extension where kanbanr installed them.
2. Stop anything long-running on each board, such as `kanbanr serve`.
3. Run `kanbanr migrate` once per board. It checks every approval against the board's git history,
   makes one commit and prints what it did. [Upgrading a board to schema 5](schema-5.md) has the
   details, including how to compare approval states before and after.
4. Restart `kanbanr serve`.

Everyone who uses a board needs 0.2.0 once it is migrated. An older kanbanr refuses a migrated
board and names the version it needs; it never misreads it. The minimum Rust version for building
from source is now 1.89.
