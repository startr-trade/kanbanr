# v0.3.0 — After 0.2.0

_Released 2026-10-21._

## What shipped

### FEAT-212 — Release stages that act: move main, then tag it

Each release stage is a guarded state with conditions and entry actions, so a release prepares itself, moves main first, and is tagged only once main holds the release tip and that commit is pushed, with a one-click cut that says what it will do

- THE SYSTEM SHALL read each release stage's conditions and entry actions from cadence.release_gates, keyed by stage name, keeping cadence.release_stages a list of names
- IF a release gate names an unknown stage, check or action, or orders prepare, move_main and tag against the rules, THEN THE SYSTEM SHALL refuse the configuration and say why
- WHILE a stage declares no gate, THE SYSTEM SHALL act as before: the first stage makes the branch, the last tags and fast-forwards main
- WHEN a release is promoted, THE SYSTEM SHALL work out every condition and step of the stages entered or passed before changing anything, and refuse with every missing condition and its fix if any fails
- WHEN a stage with move_main is entered, THE SYSTEM SHALL fast-forward main to the release tip without tagging, refusing if main has commits the release lacks
- WHEN a stage with tag is entered, THE SYSTEM SHALL tag the release tip only when main is at it and its required conditions hold
- THE SYSTEM SHALL judge pushed from main's remote-tracking branch, fetching first when applying, using the last-fetched refs when the fetch fails, and SHALL never push
- WHEN a stage with prepare is entered, THE SYSTEM SHALL commit the version files, the dated changelog heading, its copies, the notes draft and listings onto release/<V> in one commit, without checking anything out
- IF a version file is missing or its match finds nothing, THEN THE SYSTEM SHALL refuse the promotion and change nothing
- WHILE nothing is configured to prepare, THE SYSTEM SHALL bump no version, say so in the plan, and make no commit
- IF a step or the board write fails after earlier steps, THEN THE SYSTEM SHALL undo every git step in reverse order
- THE SYSTEM SHALL show on each unshipped release one button naming its next step, with what it will do and, for the cut, its preview, enabled only when the plan is ready, and otherwise what is missing
- WHEN release promote --plan is run, THE SYSTEM SHALL print the plan and change nothing; after a promotion it SHALL print what is next
- IF the release tip differs from the plan the caller saw, THEN THE SYSTEM SHALL refuse the promotion
- THE SYSTEM SHALL keep release_gates and release_prepare across cadence writes that do not name them
- WHEN a release is taken through candidate, main and production as 0.2.1 was, THE SYSTEM SHALL prepare it, move main, refuse the cut until main is pushed, then tag main's tip without pushing
- IF a release has no items planned into it, THEN THE SYSTEM SHALL refuse to promote it to any stage, change nothing, and offer no promote button, saying how to plan items in

### FEAT-213 — The Workflow page shows the cadence, the git model and every guard rail

The monitor's Workflow page shows in one place how work moves from an item branch to a tagged release, and every guard rail that will refuse a step on the way

- THE SYSTEM SHALL report, in one read, the method's parts, the commit rules, diagram strictness, coverage rules and the board's push policy
- WHEN the monitor asks for the git model or git doctor, THE SYSTEM SHALL answer from the code repository the daemon was started in
- THE SYSTEM SHALL show on the Workflow page the cadence, the git model and the guard rails, each with the command that changes it, read-only

### FEAT-214 — Agent scopes: what a sub-agent may do, enforced by kanbanr

kanbanr enforces what each sub-agent may do: the coordinator issues a scope per agent with one command, recorded on the board and bound to the agent's worktree; every board write, commit and push from that worktree is checked against it, anything outside it is refused and named, and the agent's own progress is recorded and attributed

- WHEN the coordinator runs kanbanr scope issue <role> <CODE>, THE SYSTEM SHALL record the scope on the board with its issuer, item, operations, branch, issue time and expiry, and print the boundary table and claim command for the brief
- WHEN kanbanr scope claim runs in a linked worktree, THE SYSTEM SHALL bind the scope to that worktree on the board and in the worktree's git directory
- IF a board write under a scope is outside its operations or its item, THEN THE SYSTEM SHALL refuse it before anything changes and name the scope and the boundary crossed
- IF a board write or commit comes from an agent worktree with no valid scope bound to it, THEN THE SYSTEM SHALL refuse it
- IF a commit under a scope is on another branch, does not name the scope's item, or is made under a design, expired or revoked scope, THEN THE SYSTEM SHALL refuse it in the commit guard and the git hooks
- IF a process in an agent worktree pushes the board or the code, THEN THE SYSTEM SHALL refuse it
- THE SYSTEM SHALL record each write and commit made under a scope as the person, by the agent for its item, in the activity entry, the event, the board commit and the code commit
- WHEN a scope is revoked or its expiry passes, THE SYSTEM SHALL refuse every further write and commit under it
- WHEN a build scope's branch has commits newer than its item's last task change, THE SYSTEM SHALL name them in the Stop hook, git doctor and session start
- THE SYSTEM SHALL show each project's scopes and their state on the monitor's item page and Workflow page
- WHERE no scope applies, THE SYSTEM SHALL behave as before
- THE SYSTEM SHALL state in the skill that Claude issues a scope with one command before starting each sub-agent, starts it in its own worktree, and puts the generated brief into its brief
- IF a command run in an agent worktree would change kanbanr's own enforcement or write outside the board's write path, THEN THE SYSTEM SHALL refuse it
- IF a task change under a scope would complete its item, THEN THE SYSTEM SHALL keep the item where it is and say the coordinator moves it

### FEAT-215 — The skill states what each sub-agent may do

In every project using kanbanr, Claude briefs each sub-agent with precise boundaries for its role, build agents record their own progress, and the board never lags the code

- THE SYSTEM SHALL state in the skill, for each sub-agent role, what it may and may not do, and the coordinator's duty to brief it and keep the board current
