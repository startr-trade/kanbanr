# kanbanr 0.3.0 — releases that run themselves, and sub-agents that stay in bounds

*Released 21 October 2026.*

Two things this release changes about how work leaves your hands. A release now moves through its
stages doing what each stage is for: it prepares its own version and notes, moves main, and is
tagged only once main has been pushed and CI has seen it. And when Claude hands work to a
sub-agent, kanbanr now enforces what that agent may do, instead of leaving it to the brief.

No board migration is needed: 0.3.0 reads the schema-5 boards 0.2.x left.

## What's new

- **Release stages that act.** Each release stage can say what must be true before a release
  enters it and what happens when it does: make the release branch, prepare the release, move main,
  tag it.
  - **A release prepares itself.** Entering the first stage commits the version bump in every file
    you name, the dated changelog heading, and draft notes from the release's items onto
    `release/<V>`, without checking anything out. No separate item is needed to get a release ready.
  - **Main moves before the tag.** A stage can fast-forward main to the release without tagging, so
    you push main and let CI run on exactly the commit that will be tagged.
  - **The cut waits for your push.** The last stage can require that main is at the release and that
    commit is on `origin/main`. Until then, the Releases page shows **Cut v0.3.0** greyed out and
    says what is missing: "push main, then wait for CI".
  - **One button per release**, named for its next step, showing what it will do. The cut is one
    click, with its preview beside it: the commit it tags, what ships, what carries over.
  - **A release with nothing in it can't be promoted.** The page says how to plan items in.
  - Set it up with `kanbanr config release-stage` and `kanbanr config release-prepare`; see what
    each stage does with `kanbanr release stages`, and what a promotion would do with
    `kanbanr release promote <V> --plan`. Projects that set nothing keep the stages they had.
  - See [Processes](../using/processes.md).
- **Agent scopes: what a sub-agent may do, enforced.** Before Claude starts a sub-agent, it issues
  a scope with one command (`kanbanr scope issue build <CODE>`), and puts the brief kanbanr prints
  at the top of the agent's instructions.
  - The agent claims the scope in its own worktree. From then on, every board write, commit and
    push from there is checked against it: a build agent may record its own item's task states and
    test results and commit on its item's branch; a design agent may only read. Anything else is
    refused, and the refusal names the boundary it crossed.
  - Agents never push; the new pre-push hook and the commit guard refuse it.
  - What an agent records is attributed to you, "by the agent for <CODE>", in the activity, the
    events and the commit trailers.
  - If an agent's commits run ahead of its item's tasks, the Stop hook, `kanbanr git doctor` and the
    start of the next session name it.
  - The item's page shows its agents, and the Workflow page lists every scope.
  - See [Working with Claude](../using/with-claude.md).
- **The Workflow page shows how work moves.** Below the stages: the sprint and how often releases
  are cut, with their stages in order; the git model, from where items branch to where production
  moves and what kanbanr merges; and every guard rail on the project, each with the command that
  changes it.
- **The skill says what each sub-agent may do**, so the same boundaries apply in every project
  that uses kanbanr.

## What's fixed

- `release add <V> --branch` is gone: a new release has no items yet, so it could not be promoted.
  Start a release with `release plan`, then promote it to candidate.
- `kanbanr activity` now names the agent a write was made by, as the monitor does.

## Upgrade notes

1. Update with `kanbanr self-update` (macOS, Linux) or by rerunning the installer (Windows).
2. Run `kanbanr git install-hooks` once in each project folder, to add the new pre-push hook.
   Issuing an agent scope needs it.
3. Restart `kanbanr serve`.

Boards need nothing. Release stages that act, and agent scopes, change nothing until you set them
up or issue one. Once a board holds a scope, a sub-agent's worktree that has not claimed one is
refused board writes and commits there.
