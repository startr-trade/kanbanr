# v0.7.0 — The system view

_Released 2026-11-16._

## What shipped

### DEF-047 — The docs_updated gate ignores board docs linked under a design's Affects docs

A docs_updated gate that also reads the board docs a design links under Affects docs, for the person relying on the gate, so that an item cannot pass it with the docs its design names unchanged

- WHEN a move passes through a gate listing docs_updated, THE SYSTEM SHALL also require each board doc linked under the item's Design Affects docs to have changed since the item entered its stage, and SHALL name each one that has not

### DEF-049 — A release reads as shipped before its tag's workflow has passed

A release that reads as shipped only once the workflow its tag started has passed, for the person releasing, so that the board never claims a release is out when its publishing failed

- WHEN a release is cut, THE SYSTEM SHALL show it as tagged, not shipped, until a passed result is recorded for the workflow its tag started
- IF the tag workflow result is recorded as failed, THEN THE SYSTEM SHALL keep the release tagged and name the patch release as the way on

### DEF-051 — Sprint close asks about each merged branch, and agent branches are left behind

Merged and finished-agent branches cleaned up after one confirmation, for the person closing a sprint, so that leftovers take one answer, not one per branch

- WHEN a sprint closes, THE SYSTEM SHALL list merged item branches and finished agents branches and delete them locally after one confirmation, and SHALL never delete an unmerged branch or touch the remote
- WHEN a build scope is revoked and its agent branch is merged, THE SYSTEM SHALL delete that branch

### DEF-053 — A board's README names kanbanr, not the project it tracks

A board whose README names and links the project it tracks, for someone who opens the board on its remote server, so that they see whose plan it is before they see the tool that keeps it

- WHEN the board's README is generated THE SYSTEM SHALL name the board's projects in its heading and link each project's recorded code repository
- WHEN a project is set up in a folder with a git remote THE SYSTEM SHALL record that remote as the project's code repository
- WHERE a board has a remote and a project has no recorded repository THE SYSTEM SHALL name the project in doctor with the command to add one

### DEF-056 — Claude doesn't prepare a project's first release: release files, the pipeline and override checks

A first release Claude prepares before the person is asked to promote it, for a person releasing through Claude, so that the candidate has its notes, changelog and pipeline and no override is made on a gap already closed

- WHEN a project's first release is planned THE SYSTEM SHALL have Claude propose release-prepare and, where setup recorded CI, a pipeline item, before it names Promote to candidate
- WHEN Claude is about to override a gate THE SYSTEM SHALL have it run kanbanr check again first
- WHEN Claude files a chore itself, THE SYSTEM SHALL have it ask the once-only questions (a statement, a goal and an EARS requirement) as for a chore the person asks for

### DEF-058 — A build in a git worktree keeps the commit of its first build

A kanbanr built in a git worktree that names the commit it was built from, for anyone checking an install, so that --version is true after the worktree moves

- WHEN a build runs in a git worktree whose HEAD has moved since the last build THE SYSTEM SHALL stamp the binary with the new commit

### DEF-060 — A granted delegation can't be used when Claude Code runs in auto mode

A delegation that Claude can use under Claude Code's auto mode, for a person who granted one, so that a decision they delegated is taken without their click

- WHEN a delegation is granted and the project is in delegated mode THE SYSTEM SHALL offer the Claude Code permission rule that lets Claude run the delegated command

### DEF-061 — kanbanr capture records nothing from Vitest 5, pytest -v or Playwright runs

Test results read from a Vitest 5, pytest -v or Playwright list-reporter run, for a project with a JavaScript or Python code base, so that its passing tests count as evidence without a workaround

- WHEN a captured run prints Vitest 5 result lines ending in a duration THE SYSTEM SHALL record each test's result under its name without the duration
- WHEN a captured run prints pytest -v result lines (`<node id> PASSED|FAILED|ERROR|SKIPPED|XFAIL|XPASS`, followed or not by the progress `[ 25%]`), THE SYSTEM SHALL record PASSED as green and FAILED or ERROR as red under the node id as printed (`tests/test_repository.py::test_x`), and SHALL record nothing for SKIPPED, XFAIL and XPASS
- WHEN a captured run prints Playwright list-reporter result lines (`✓|✘|-  <n> [<project>] › <file>:<line>:<col> › <titles> (<duration>)`), THE SYSTEM SHALL record ✓ as green and ✘ as red under `<file> › <titles>` and under `<titles>` (project, location, retry mark and duration dropped), SHALL record nothing for `-`, and SHALL record a name red when any of its lines in the run failed

### DEF-063 — The stop check counts a sprint catch-up merge as agent work ahead of the board

A stop check that counts only a build agent's own commits, for the person whose session it holds open, so that a sprint catch-up merge never reads as agent work ahead of the board

- WHEN a build scope's branch holds a commit that main, a sprint branch or a release branch already holds, THE SYSTEM SHALL not count it as the agent's work ahead of the board
- THE SYSTEM SHALL not count a merge commit on a build scope's branch as the agent's work ahead of the board
- WHEN a build scope's branch has a non-merge commit of its own that no line holds, committed after its item's tasks last changed, THE SYSTEM SHALL name that commit, and only such commits, in `kanbanr scope drift`, the Stop hook, session start and `kanbanr git doctor`

### DEF-064 — Ratifying an override at an already-ratified definition rev records nothing, and the Review page keeps asking

A ratification that records each override Claude made, even at a definition revision the person already ratified, and a disabled Ratify button that says why, for the person reviewing, so that an override never waits forever and a dead button never hides its reason

- WHEN the person ratifies an item that has an override Claude made after its last ratification, at a definition revision already ratified, THE SYSTEM SHALL record a new ratified approval event and close that override, so the Review page and kanbanr check stop asking
- IF a ratification repeats the latest one on an unchanged definition and no override Claude made waits for one, THEN THE SYSTEM SHALL record nothing and answer who ratified it first, when and from where
- WHILE the Approve or Ratify button on the Review page is disabled, THE SYSTEM SHALL show beside it one sentence that says what is missing and who provides it

### DEF-065 — The Claude docs guard judges a worktree's files by the main checkout's path and refuses the book, the changelog and the skill

A Claude docs guard that judges a written file by the git top level of the folder the file is in, for build agents working in linked worktrees, so that the book, the changelog and the skill are not refused there

- WHERE a markdown file inside a linked git worktree is part of what the repository ships (the book, the changelog, the skill, a fixture), THE SYSTEM SHALL allow it, judging it by its path relative to that worktree's own top level
- WHEN a stray markdown file such as notes.md is written at the root of a linked git worktree, THE SYSTEM SHALL still deny it
- WHEN the guard refuses a file in a linked git worktree, THE SYSTEM SHALL suggest a board path built from the path relative to that worktree's top level and SHALL leave the refusal message unchanged
- WHEN a `git commit` targets a repository outside the project's checkout and its linked worktrees (a scratch repository under the temporary folder, for example), THE SYSTEM SHALL not apply this board's rules to it: a repository with no `.kanbanr` marker is left alone, and one with its own marker is judged by the board that marker names ([FEAT-127](/p/kanbanr/feature/FEAT-127))

### DEF-066 — A position on a checkout with line-ending conversion reads dirty, where katalogr's contract now says clean

A position that compares each working file in its repository form, after git's to-git conversion, for the person and the two tools reading one checkout, so that a checkout with line-ending conversion reads clean where katalogr's contract says clean and both tools give it the same position and view ID

- THE SYSTEM SHALL compute, for every case of the shared file fixtures/contract/position-v1.json as katalogr's v0.2.0 holds it (blob 3cd6f5d0), exactly its expected position text, the line_endings case (core.autocrlf=true, `* text=auto`, a CRLF worktree over an LF blob) included, which is the commit alone
- THE SYSTEM SHALL compare each tracked regular file with its HEAD blob in its repository form, the bytes git's to-git conversion stores under core.autocrlf, core.eol and the text, eol, crlf and ident attributes, and SHALL put the repository-form blob id in the dirty hash for a changed or untracked file; a file whose raw bytes already hash to its HEAD blob, a symbolic link's target and a path that is not UTF-8 SHALL be taken as raw bytes, and IF a path has a driver filter (filter=<name>) or the conversion fails, THEN THE SYSTEM SHALL take its raw bytes and start no process
- WHEN a view reads an uncommitted file whose raw bytes differ from its repository form, THE SYSTEM SHALL serve the repository-form bytes, which hash to the blob id the position recorded, so that a CRLF checkout and an LF checkout holding the same content give the same view bytes and the same view ID
- THE SYSTEM SHALL give, on a checkout with no line-ending conversion configured, positions byte-identical to the raw-bytes reading; SHALL convert no tracked file whose raw bytes hash to its HEAD blob; and SHALL give the same position whatever the number of threads that read the checkout
- WHERE a checkout holds 10,000 tracked text files, THE SYSTEM SHALL read its clean position within 200 ms with LF line endings (FTR-003 R-10, unchanged) and within 300 ms when core.autocrlf=true has checked every file out with CRLF (release build, warm, three reads, median; twice the budget above a load average of 4)

### DEF-068 — A Python standard-library project's unittest results are never captured, so no test reaches green

Test results read from a `python -m unittest -v` run, and a notice when a test run prints nothing the capture hook can read, for a project whose tests use Python's standard library, so that its passing tests count as evidence and Claude learns at once when a run recorded nothing

- WHEN a captured run prints unittest verbose result lines (`<name> (<module>.<Class>.<name>) ... ok|FAIL|ERROR|skipped …|expected failure|unexpected success`, the Python 3.10 form `<name> (<module>.<Class>) ...`, a docstring's two-line form, or a subtest's `(<params>)` line), THE SYSTEM SHALL record `ok` as green and FAIL, ERROR or unexpected success as red under `<module>.<Class>.<name>`, SHALL record nothing for skipped and expected failure, and SHALL record a name red when any of its lines failed
- WHEN the capture hook sees a command that runs tests (cargo test or nextest, pytest, python -m unittest, npm/pnpm/yarn test, vitest, jest, playwright test, go test, mvn, gradle, dotnet test, rspec, make test) and reads no test result from its output, THE SYSTEM SHALL tell Claude, in the hook's answer, that nothing was recorded and which runner forms it reads, and SHALL say nothing when it read a result or the command runs no tests

### FTR-003 — A shared position, and a view ID

A position (a commit plus a hash of uncommitted changes) and a view ID that kanbanr computes byte-identically with katalogr, for the person and the two tools so that a view answered by either can be compared, repeated and trusted at any position

- THE SYSTEM SHALL represent a position per repository as a commit plus a dirty hash in the text and JSON forms of chain decision CD-2, naming the repository by the board's project id; IF given text that is not a valid position, THEN THE SYSTEM SHALL refuse it as a usage error (exit 2)
- THE SYSTEM SHALL compute the dirty hash as the SHA-256 of the sorted lines of path and raw blob id, or `-` for a deleted path, for every path whose raw worktree bytes differ from HEAD and every untracked path not ignored; staging and file modes SHALL not change it, and a repository with no commit yet SHALL have commit null
- THE SYSTEM SHALL compute, for every case of the shared file `fixtures/contract/position-v1.json`, exactly its expected position text, and the file SHALL stay plain data identical to katalogr's copy
- WHEN an answer is exact, THE SYSTEM SHALL carry a view ID in chain decision CD-3's format whose facts part is the SHA-256 of the board's HEAD commit and the project's facts revision, so that the same question at the same position with the same board commit repeats its ID, a different position, question, board commit or facts record gives another, and the binary's version takes no part
- THE SYSTEM SHALL make a view a function of its position, the board and the project's facts alone: two exact answers to one question at one position with one board commit SHALL be byte-identical, and the body SHALL hold no clock, host name, watermark or absolute path
- WHEN a read names a position with `--at` (or `at=`), THE SYSTEM SHALL answer a clean position from the commit's objects with nothing checked out, and a dirty position only while the checkout is at it; IF neither holds, THEN THE SYSTEM SHALL answer nothing, exit 6 (HTTP 409), and name the position it does hold
- THE SYSTEM SHALL say on every view answer which position it reflects and whether it is exact; IF an uncommitted file changes while a view is read, THEN THE SYSTEM SHALL read the position again once and, failing that, answer not exact with no view ID and a warning
- THE SYSTEM SHALL offer `kanbanr position [--json]`, printing the checkout's live position with no board needed, and `kanbanr view docs [--root R] [--max-nodes N] [--at P] [--json]`, and SHALL serve both through the daemon at GET /projects/{p}/position and GET /projects/{p}/views/docs, reading the repository the daemon was started in
- THE SYSTEM SHALL carry warnings with a view answer and show them wherever the answer is shown (one `warning:` line each on stderr, the `warnings` field in JSON), including, for a view answered for a repository with no checkout on this machine, the warning that its position is an imported snapshot's commit and uncommitted changes there cannot be seen
- WHERE a checkout holds 10,000 tracked files, THE SYSTEM SHALL read its position within the budget SPK-001's result sets (proposed 200 ms, warm, idle machine), and SHALL compute a view ID within 100 µs
- THE SYSTEM SHALL add the position and view routes additively under the published read API, regenerate the OpenAPI document, keep every board file and schema unchanged, and add no C build dependency

### FTR-037 — Walkthroughs that run themselves: the guide's runs driven headlessly, decisions taken on the scratch board by a scripted person, every question and board claim captured

A walkthrough that runs itself through `kanbanr walkthrough`, for the maintainer who accepts a release, so that a guide's runs are checked on every release without the person's hours, and the person's own check shrinks to what only a person can judge

- WHEN a run starts, THE SYSTEM SHALL refuse to start unless the run's project and board are inside KANBANR_BOARD_FENCE and its remotes are the run's own, and SHALL write setup.log naming the installed kanbanr and its commit, the skill's tree checksum, the Claude Code version, the model and the checksums of the person's rules
- WHEN Claude asks a question during a run, THE SYSTEM SHALL answer it from the runbook's policy, else the recommended option, else the first option, SHALL log the question, its options, the pick and which policy chose it, and SHALL never stop the run for a question
- WHEN a runbook step names a decision, THE SYSTEM SHALL take it as the scripted person through the monitor's write route on the fenced board, or by pressing the named button on the rendered page when the step says press, SHALL check that the offer the guide names is present first, and SHALL record a finding, not a stop, when the offer is absent or the board's claim differs from the truth it fetched
- WHEN a run ends, THE SYSTEM SHALL keep every raw capture (transcript, board bundle and copy, monitor log, screenshots, remote refs and tags, CI results, questions.tsv, prepared.tsv, truth.txt, setup.log) under a manifest of checksums, and SHALL derive decisions.tsv and metrics.md from the captures alone so that a second derive is byte-identical
- WHEN a run's checks are recorded, THE SYSTEM SHALL prepare them on the target board as one batch naming the run, and the Review page SHALL let the person confirm or reject the whole batch with one click, or one result alone
- WHEN a definition names a test of kind walkthrough, THE SYSTEM SHALL count it as automated evidence in check, drift and the retro once a run has recorded it, and SHALL never ask the person to run it by hand
- WHERE a run is started with a budget, THE SYSTEM SHALL stop the developer's session at that budget and record the stop as a finding, and a full guide run SHALL finish within 3 hours of wall time on the maintainer's machine
- WHEN the person wants to take the decisions themselves, THE SYSTEM SHALL run with --pause-at-decisions, waiting at each decision step until the person has acted on the monitor, and SHALL otherwise behave the same
- WHILE a run is in progress, THE SYSTEM SHALL write nothing outside the run's folder, its scratch board, its own remotes and the target board's prepared records, and SHALL refuse a push to any other remote
