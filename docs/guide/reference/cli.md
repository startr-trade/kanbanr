# Command reference

## Complete command reference

Everything the CLI does, grouped by what you are trying to find out. `--json` works on every read and prints one JSON document. The four exceptions have a named format or a document body as their payload: `export`, `graph` and `gantt` take `--format`, and `doc show` prints the file.

**Setting up and looking around**

| Command | What it does |
|---|---|
| `kanbanr init <name> [--repository URL\|""] [--repository-private on\|off]` | data folder + git repo + identity + project, in one step; records the folder's git remote as the project's code repository, linked from the board README (`""` records none, `--repository-private on` names it without a link) |
| `kanbanr project init/edit/list/use/delete` | create, rename, select (writes the `.kanbanr` marker); `edit` also takes `--repository URL\|""` and `--repository-private on\|off` |
| `kanbanr where [--json]` | which board folder this directory uses, and why |
| `kanbanr whoami` / `kanbanr identity` | the commit identity this data folder writes as |
| `kanbanr config show / set-transition / displayed-states / default-state / no-op-states / workflow` | the workflow; `config workflow --preset <name>`, `--from-file`, `--export`, `--write-agreement` ([Processes](../using/processes.md)) |
| `kanbanr config rename-status <OLD> <NEW>` | rename a status and move every item in it |
| `kanbanr config cadence [--sprints on\|off] [--releases on\|off] [--unit points\|days] [--release-stages a,b,c] [--integration-branch B] [--main-branch B] [--git-model on\|off] [--has-ci on\|off]` | switch sprints, releases and the estimate unit on or off for a project; name the stages a release moves through (the last is the cut) and the branches promotion uses; let the git model drive branching (on by default once sprints or releases are chosen); say the project has CI, so the recommended `tag` stage waits for it. Turning releases on with no stages named gives `candidate`, `main` and `tag` ([Release stages](../using/processes.md#release-stages)); a stage that does nothing is warned about |
| `kanbanr config method [--on\|--off] [part…]` | the method — design before build, docs kept current, broken references reported — part by part: shown, turned off, or back on |
| `kanbanr config coverage [--from-file F \| --clear]` | the project's architecture coverage rules: with no flag, each rule with how many of its subjects are uncovered and its source doc; `--from-file` sets them from YAML (refused, naming the rule, if invalid), `--clear` removes them |
| `kanbanr config diagrams [--strict on\|off]` | whether a write whose Mermaid diagrams fail the lint is refused (strict) or written with the problems printed as warnings (the default); with no flag, shows the setting |
| `kanbanr config codes [--set KIND=PREFIX,…] [--unset KIND,…] [--default PREFIX\|""] [--clear]` | which prefix a new item's code gets from its kind (`defect=DEF` codes a defect `DEF-001`, with a counter per prefix); with no flag, each kind's prefix, the default (`FEAT` unless set) and the next code per prefix. A prefix is 2–6 uppercase letters, not `MS`, `ADR`, `SC`, `SP`, `TL` or a milestone's; a bad one is refused, naming the entry. Existing codes are never renamed; unset, every item is `FEAT-` |
| `kanbanr config build [--slots N] [--jobs-per-slot N] [--reserve-cpus N] [--reserve-mem-gib N] [--max-load F] [--sccache auto\|off] [--cache-gib N] [--linker default\|mold] [--web-cache on\|off] [--queue-batch N] [--line-check "<cmd>"]` | how agents' builds share the machine (FTR-062); `""` clears a setting. With no flag, each effective value and where it came from: the default leaves 2 vCPUs free and gives each slot 5 jobs |
| `kanbanr hooks install / status / uninstall` | the Claude Code hooks (session start, stop nudge, test capture, commit guard). The Bash guard, the Write guard and test capture also tell a sub-agent (its calls carry an `agent_id`) from the coordinator: an agent scope applies to agents only, and `scope issue` needs these hooks |
| `kanbanr serve [--ui-dir …] [--allow-writes] [--allow-remote-writes]` | the monitor over this board; read-only unless `--allow-writes`, and then it takes writes only from its own page, or from an https origin named in `KANBANR_ALLOWED_ORIGINS` (comma-separated, such as `https://board.example.com`). With writes on it refuses to start on an address other machines can reach unless `--allow-remote-writes` or `KANBANR_ALLOW_REMOTE_WRITES=1` accepts it. It answers for `localhost`, `127.0.0.1`, `[::1]`, its bound address and the hosts in `KANBANR_ALLOWED_HOSTS` (comma-separated `name[:port]`, for a reverse proxy); any other host gets a 403 |
| `kanbanr serve --board PATH [--board PATH …] [--ui-dir …]` | one read-only monitor over several boards, in the order given: their projects are served together, each read from its own board, and the boards are listed at `/api/boards` and on the home page. A board's name is the last folder name of its path as written. `--board` replaces the data folder, so `KANBANR_DATA_DIR` is ignored and no code repository is looked for. Refused before anything binds, exit 1: with `--data-dir` (`--board and --data-dir cannot be used together: --board names every board this server shows`), with `--allow-writes` or `--allow-remote-writes` (`--board serves boards read-only; --allow-writes and --allow-remote-writes are refused with it`), a path with no folder name, a path with no `projects/` folder, two boards of one name, and one project on two boards. See [Several boards on one server](../using/the-monitor.md#several-boards-on-one-server) |
| `kanbanr open` | open the running monitor in a browser |
| `kanbanr open --check [--json]` | report, opening nothing, whether the monitor is up and accepts writes, and its Review and Releases addresses |
| `kanbanr self-update [--check]` | replace this binary with the release's, checksum-verified (and the skill and editor extension already installed) |
| `kanbanr skill install / status / uninstall` | the Claude Code skill this program carries, in `~/.claude/skills/kanbanr` |
| `kanbanr editor install [--editor codium] [--if-installed]` | this release's VS Code extension, checksum-verified, into the editors on PATH |

**The work**

| Command | What it does |
|---|---|
| `kanbanr board` / `kanbanr feature list / show / add / edit` | the kanban and its items |
| `kanbanr recover [--budget BYTES]` | the plan to resume from, sized for a session start (what the SessionStart hook prints): the whole summary when it fits the budget, else a brief form with the counts per status, every item in progress, what waits for you, the sprint and release, and where to read more. The budget is `--budget`, else `KANBANR_SESSION_BUDGET`, else 8000 bytes, never below 2000; `--json` gives `{bytes, form, text}`. With no project it prints nothing and succeeds |
| `kanbanr move <CODE> <STATUS> [--override "…"]` | a status change, validated against the workflow and the stage's gate; `--override` passes a gate and records why. Merging an item into a release past its first stage sends the release back to that stage and prints the steps from there; a release tagged and not shipped refuses the merge |
| `kanbanr start <CODE>` / `kanbanr finish <CODE>` | begin (branch, active stage) and end an item, each through its gate |
| `kanbanr planning list [--state pending\|carried\|declined] [--json]` / `planning show PD-n` / `planning check PD-n` / `planning decline PD-n --reason "…" [--nearest into-release:v0.9.0]` | the person's planning decisions made on the monitor pages (FTR-049): one line each with its state; show one; check one with nothing changed (problems, warnings, nearest move); decline one with a reason. There is no command to record one |
| `kanbanr sprint plan <SP> <CODE>… --decision PD-n` / `sprint unplan <CODE>… --decision PD-n` / `release plan <V> <CODE>… --decision PD-n` | carry out a pending planning decision: refused unless it is pending and its action, target and items equal the command's; the plan change and the decision's outcome are one commit, and the outcome's `by` and `origin` say who ran it |
| `kanbanr milestone add / list / edit / delete` | milestones (a dependency DAG; cycles rejected); list prints newest first; `--oldest-first` gives creation order |
| `kanbanr todo add / list`, `kanbanr task add / state / list` | persistent todo-lists on an item; `task state … completed [--tokens N] [--cost-usd X] [--model M]` keeps what the task cost in the task log, with its builds since it last went in progress read from the build log (FTR-061) |
| `kanbanr task add <CODE> <TL> --text … [--key T3] [--after T1,TL-002/T2,FTR-041/TL-001/T1] [--writes a,b] [--reads c] [--estimate 2h]` / `task edit <CODE> <TL> <KEY> [--text …] [--after …] [--writes …] [--reads …] [--estimate …]` | what a task records beside its state (FTR-060): the tasks it waits on (same list, another list of the item, or `CODE/TL-001/T3` in another item), the files it writes and only reads (repository-relative, a folder ends in `/`), and its estimate in agent-hours (`90m`, `2h`, `1.5h` or a bare number of hours). An unknown or cyclic dependency, a bad path and an estimate of 0 are refused. `task edit` never changes the state; an empty value (`--after ""`) clears that field; a Completed task can still be edited. `task list` shows each task's AFTER, WRITES (a count), ESTIMATE and SCOPE (the live scope working it) |
| `kanbanr todo from-design <CODE> [--todo TL-001] [--apply] [--json]` | mirror the item's Design implementation tasks into a todo-list (FTR-060): reads the spec's `Implementation tasks` heading, each `- **T<n>**` bullet with its `Depends on …`, `Writes: …`, `Reads: …` and the estimate in its trailing tag (`[sonnet, 2 h]`). The dry run lists each task as new, changed (naming the fields) or unchanged, a board task the Design does not name (kept, never deleted), and a dependency on another item's task it cannot place in one list (not applied); `--apply` writes the adds and edits in one batch, one commit. It never changes a task's state. The default list is the one whose description starts "Build (from the Design", else the newest, else a new one |
| `kanbanr export <CODE> --format md\|json` | one item, rendered for a human or a machine |
| `kanbanr query "text" [--goal G-1] [--gap …] [--all-projects]` | rich filters plus full text, across projects |
| `kanbanr activity` / `kanbanr events` | the changelog, and the notification event log |
| `kanbanr doc folder / add / tree / list / show / rm` | the documentation tree. `doc show <PATH> --at <PICK>` reads `PATH` from the code repository instead, at a pick: `main`, `worktree`, an item code, a sprint code, a release version or a commit. It prints one line saying what was read (path, position, from git or disk), a blank line, then the text; `--json` prints the answer. Run it from the project folder. Exits 1 when the doc is not there (the reason names the position and whether `main` has it) and 6 when no checkout holds the position |

**Process: definitions, agreement and sign-off**

| Command | What it does |
|---|---|
| `kanbanr charter show / set` | why the project exists: purpose, goals, non-goals, constraints |
| `kanbanr feature define <CODE> [--file …] [--template]` | an item's definition: statement, goals, Zachman, requirements and their tests |
| `kanbanr signoff <CODE> <name>` | record a named sign-off a stage's gate asks for, pinned to the current definition |
| `kanbanr signoff <CODE> <name> --withdraw --reason "…"` | takes a sign-off back; the earlier one stays on the record and stops counting |
| `kanbanr ratify <CODE>` | agree after the fact to work started under a recorded override |
| `kanbanr test <CODE> <R-n> <test> planned\|red\|green` / `kanbanr tests [--write] [--json]` | move a test along its lifecycle (`--note TEXT` is kept with a manual test's result, which a person records on the Review page's Manual checks and Claude is refused); reconcile the board's evidence with the code, run from the project folder: results whose test is not defined under its name (with the revision last recorded and a likely rename), greens at a revision that never held the test, tests never run or failing, unproven requirements on finished items, open manual checks per item and per release, and finished items with no definition. `--write` returns the vanished results to planned, naming each and its revision in the commit; outside a git repository the report says revisions were not checked |
| `kanbanr defect <CODE> …` | what a defect cost and where it came from |

**The engineering baseline: practice packs**

| Command | What it does |
|---|---|
| `kanbanr profile list` | every practice pack this board can apply: the board's (`profiles/`), your personal ones (`~/.kanbanr/profiles`, or `KANBANR_PROFILES_DIR`) and the ten built-in ones, with versions and the projects that follow each. Needs no board |
| `kanbanr profile show <NAME>` | a pack's file, found by name: the board's, then yours, then the built-in one |
| `kanbanr profile check <FILE\|-\|NAME>` | check a pack without applying it: its problems, then its warnings, or `checks clean: N areas (M at setup), K options`. Changes nothing; exits non-zero on a problem |
| `kanbanr profile save <NAME> [--from-file F\|-] [--personal] [--description …]` | save a pack to the board (one commit) or to your personal library: from a file, or by default this project's applied copy of the pack. It must check clean; the version goes up only when the content changed |
| `kanbanr profile add <NAME>` / `kanbanr profile remove <NAME>` | follow a pack in this project, or stop following it; removing keeps every answer and entry, and adding it again brings them back. Prints what changed and `answers kept: N` |
| `kanbanr profile ask [--at setup\|first_need] [--item CODE] [--answers F] [--explain AREA]` | what to ask now, as JSON: the open areas of the packs the project follows (setup: `core` when none is chosen yet), the detected option first, else the recommended one, in dialogs of at most four, and the packs the facts suggest. `--item` reads that item's Design and implies `first_need`; `--answers` counts a scratch answers file as given; `--explain` prints each option's `why`, `fits_when` and `costs` with the facts and files that bear on it. Changes nothing |
| `kanbanr profile status [--if-changed]` | the packs this project follows and whether their libraries have moved on: new areas to answer, recommendations changed |
| `kanbanr profile diff [<NAME>]` | what differs between the project's applied copy of a pack, or of every pack it follows, and its library's current copy |
| `kanbanr profile update [<NAME>] [--dry-run]` | adopt the library's current copy of a pack, or of every pack followed, only on request; every answer is kept. `--dry-run` says what it would change and changes nothing |
| `kanbanr baseline show` | the baseline: the packs, each area as answered, proposed, open, decide-later or not applicable with its entries and ADRs, every revision, and the charter's constraints |
| `kanbanr baseline propose --answers F\|- [--item CODE] [--note …]` | propose answers as a revision (answers file: `item`, `note`, `answers: [{area, options: [..]}, {area, later: true}, {area, not_applicable: <reason>}]`; `option: <id>` reads as one option). Prints each entry it makes, each stage gate acceptance adds, and where it waits. Inert until accepted |
| `kanbanr baseline accept <REV-n> [--rev HASH]` | accept a proposed revision as it stands now (or as `--rev` pins it): its constraints get their ADRs, the release stages it names require their gates. The person's own, on the Baseline page or in their terminal: refused inside a Claude session |
| `kanbanr baseline withdraw <REV-n> --reason "…"` | withdraw a proposed revision; the record stays |

**The project's facts and its content catalog** (FTR-005)

| Command | What it does |
|---|---|
| `kanbanr facts [show] [--json]` | the project's facts record: its languages, runtimes, where it runs, its parts and its data; or `no project facts` and the command that sets them |
| `kanbanr facts set --languages L --runtimes R --production P --parts P --data D` | replace the whole facts record, each key a comma list of vocabulary words or `other:<text>`; `--from-file F` takes the record as YAML. Refused, naming each problem, for an unknown word or a record with every list empty |
| `kanbanr facts vocabulary` | the five questions and the words that answer them |
| `kanbanr catalog [show] [--json]` | the catalog's status: the gaps first (`gap: when × operator — no row answers it`), then each row by level with whether it applies (`off (why)` when switched off), its source's state and its protections. Derived on every read, never stored |
| `kanbanr catalog init [--force] [--print]` | write the starter catalog; refused when the project has one unless `--force`; `--print` prints the starter and writes nothing |
| `kanbanr catalog set --from-file F` | replace the catalog from YAML (a mapping with `rows`, or a bare list of rows); refused, naming the row, when a row is invalid |
| `kanbanr catalog add <row>` | copy one row of the starter catalog into the project's catalog |
| `kanbanr catalog off <row> --why "…"` / `kanbanr catalog on <row>` | switch a row off with the reason it does not apply, or back on, so its `when` clause decides again |

**Sprints and releases** (projects with cadence switched on)

| Command | What it does |
|---|---|
| `kanbanr sprint add / edit / remove / list / show / plan / unplan / start / close` | timeboxes: add one (`--start` takes a date or `today`; `--lanes N` and `--build-slots N` state its capacity for agent-built work, beside or instead of `--capacity`), change one that has not started (name, goal, dates, capacity, lanes and build slots, `0` clearing either), remove an empty unstarted one, list them, see one with its burndown, plan items in, take items out (`unplan`), start (a sprint dated later starts today, keeping its length), close (carrying unfinished work) |
| `kanbanr release add / remove / list / plan / cut` | releases: add one, remove an empty one that has not started (`--patch-of <V>` makes a patch of a cut release, branched from its tag, or of a tagged one whose CI failed with `--from-failed-tag [--link URL] [--notes TEXT]`, which files a defect, plans the release's items into the patch and supersedes the release; a new release starts with `release plan`, then promoting it to candidate), list them with their stage, newest first by version (a pre-release just below its release; versions that are not numbers last, in the order added; `--json` the same), plan items in, cut it (ship what is finished, write notes, carry the rest; `--tag` is promotion to production) |
| `kanbanr release promote <VERSION> [<STAGE>] [--reason … \| --note …]` | move a release to its next stage or the one named ([Release stages](../using/processes.md#release-stages)), doing what the stages it enters say: by default the first makes `release/<VERSION>` and the last is the cut — it fast-forwards main and tags the version. Any missing condition refuses it with its fix, changing nothing; a release with nothing planned into it is refused. Back a stage needs `--reason`; nothing moves back from production. Prints each step and what is next. Run it from the project folder; nothing is pushed |
| `kanbanr release promote <VERSION> [<STAGE>] --accept-untested CODE/R-n,…` / `kanbanr release cut <VERSION> --accept-untested …` | at the cut, accept shipping the requirements whose tests were not run, exactly as the plan lists them; a different list is refused as changed since. The acceptance is kept on the stage change and the notes gain "Not verified in this release" ([Tests checked later](../using/processes.md#tests-checked-later)). Your verdict: refused when Claude runs it |
| `kanbanr release promote <VERSION> [<STAGE>] --plan [--fetch]` | what that promotion would do — the button, each step, each condition with its fix, and for the cut what it tags and ships — changing nothing; `--fetch` fetches main first. Each requirement `untested_accepted` lists is printed on its own line; for a release at a stage that prepares, `again:` when entering it again would redo the preparation |
| `kanbanr release undo <VERSION> --reason … [--by NAME]` | step a stage taken by mistake back: undoes the release's newest stage change only (an earlier mistake is two undos), recording it with the reason; undoing the change that made `release/<VERSION>` deletes that branch when every commit on it is kanbanr's (`Release <VERSION>: …`), and refuses, naming it, when one is not. Refused once the release is tagged, when the stage moved main or tagged, and when the branch is on a remote or checked out in a worktree; after that the way on is a patch release. Nothing is removed from the stage history. Your verdict: refused when Claude runs it. Run it from the project folder; nothing is pushed |
| `kanbanr release notes <VERSION> [--file F \| --edit] [--changelog F] [--by NAME]` | a release's notes as they are on `release/<VERSION>`, headed with where they are (`release/v0.3.0 @ 8f995e1: docs/guide/releases/v0.3.0.md`); `--file` (`-` for stdin) or `--edit` (`$VISUAL`/`$EDITOR` on a copy) commits new text there in one commit, nothing checked out, and re-applies the notes listings; reading ends with "Not mentioned yet: …" naming the planned items the notes leave out; `--changelog` (`-` for stdin, for one of the two) commits the version's changelog section and its copies in the same commit, or alone, and refuses an empty file; a body's own heading is dropped; copies are removed; refused once the release is cut ([Reading and editing the notes](../using/processes.md#reading-and-editing-the-notes)). Notes are read from the path they were first written to, recorded on the release, so changing `config release-prepare --notes` keeps earlier releases readable; a shipped release is read at its tag, and a release recorded earlier is found at any path the setting has named. A miss lists every path and ref looked at. Run it from the project folder |
| `kanbanr release redate <VERSION> [--by NAME]` | date a release's notes and changelog heading today, in one commit onto `release/<VERSION>`, nothing checked out; main moves with it if it holds the release, and the command says to push it again; no commit when nothing is stale; refused once the release is cut ([The release date](../using/processes.md#the-release-date)). The stage that moves main does the same on its own. Run it from the project folder |
| `kanbanr release stages` | each release stage, what it requires and what entering it does, and whether that is the project's own gate or the default, and which do nothing ([Stages that act](../using/processes.md#stages-that-act)) |
| `kanbanr gate record <NAME> (--passed \| --failed) [--commit REV] [--url LINK] [--note TEXT] [--by NAME]` | record the verdict of your CI (or any gate) for a commit, as a new result beside the earlier ones; `--commit` defaults to HEAD, and a pass with no commit named is refused over uncommitted changes. kanbanr asks no server; Claude is refused this command ([Gate results](../using/processes.md#gate-results)) |
| `kanbanr gate list [--name N] [--commit REV]` | the recorded gate results, newest first |
| `kanbanr prepare gate <NAME> (--passed \| --failed) [--commit REV] [--url LINK] [--note TEXT] [--source S]… [--batch NAME]` | prepare a gate result for the person to confirm on the Releases page; `--commit` resolves as for `gate record`, and the run's link counts as a source. Nothing is recorded until they confirm ([Prepared by Claude](../using/the-monitor.md#prepared-by-claude)) |
| `kanbanr prepare signoff <CODE> <NAME> [--note TEXT] [--doc PATH] --source S… [--batch NAME]` | prepare a sign-off's note and doc for the Review page |
| `kanbanr prepare promotion <VERSION> [--stage STAGE] --checked TEXT --source S… [--batch NAME]` | prepare what was checked for a stage confirmed after the tag (default: the plan's next stage) |
| `kanbanr prepare text <CODE> <TARGET> (--still-right --why TEXT \| --correction CODE) [--source S]…` | settle one text to check under an item's docs-folded sign-off: still right, with what was compared, or the item that files the correction. `<TARGET>` is `doc:<path>`, `adr:<id>` or `item:<CODE>`, as `kanbanr check` lists it. Needs the code repository; the sign-off takes it, and the person confirms nothing ([Living docs](../using/living-docs.md)) |
| `kanbanr prepare ratify <CODE> --reason TEXT --source S… [--batch NAME]` | prepare a ratification's reason for the Review page |
| `kanbanr prepare test <CODE> <R-n> "<TEST>" (--passed \| --failed) [--note TEXT] [--rev REV] --source S…` | prepare the result of a manual test the person stated, for them to confirm on the Review page's Manual checks; `--rev` is the code commit they checked (default: HEAD). Claude is refused `kanbanr test` for a manual test ([Manual checks](../using/the-monitor.md#manual-checks)) |
| `kanbanr prepare list [--all] [--item CODE] [--release VERSION]` | the prepared records waiting for the person, newest first; `--all` adds the confirmed, rejected, superseded and stale ones, each with why |
| `kanbanr walkthrough run <runbook> [--model M] [--budget-usd B] [--max-minutes N] [--remotes PREFIX] [--pause-at-decisions] [--name NAME] [--rev COMMIT] [--no-batch]` | a guide's run, headless on a scratch board inside a fence; its checks are put on this board as one batch named for the run. Every result names the commit the binary was built from; a dirty or unknown build is refused before any session starts unless `--rev` names the commit (7 to 40 hex digits, taken as given and recorded in `raw/setup.log`). `--no-batch` puts nothing on the board ([Walkthroughs that run themselves](../project/walkthrough.md)) |
| `kanbanr walkthrough prepare --batch NAME RUN…` | one batch from several runs of one build, read from their folders alone: one result per check id, passed only if every run that measured it passed. Refuses, naming the run, a run whose setup failed, one with no `evidence_rev`, runs at two commits, a manifest that does not verify, or a check id defined differently in two runbooks; run again, it prepares nothing twice ([Release evidence: both guides](../project/walkthrough.md#release-evidence-both-guides)) |
| `kanbanr config tag-gate [<NAME>]` | the commit gate whose result judges a release's tag ([Stages after the tag](../using/processes.md#stages-after-the-tag)); with none, the first commit gate judges |
| `kanbanr config gate-docs [<ENTRY>…] [--none]` | the paths that count as documentation when a recorded gate pass is carried to a later commit: a folder ending in `/`, a suffix starting `*`, or a path; with none, goes back to `docs/` and `*.md`; `--none` carries across no change |
| `kanbanr config commit-gates [<NAME>…]` | the gates a stage requiring `gate_passed` needs a passed result of for the release tip; with none, clears them |
| `kanbanr config release-stage <STAGE> [--purpose …] [--requires a,b] [--after a,b] [--on-enter a,b] [--clear]` | a release stage's gate: conditions (`items_finished`, `prepared`, `main_at_release`, `pushed`, `gate_passed`, `tag_passed`, `items_merged`), earlier stages the release must have entered first (`--after`) and actions (`branch`, `prepare`, `move_main`, `tag`), starting from the gate in force; `--clear` goes back to the default |
| `kanbanr config release-prepare [--version-file PATH[=MATCH]]… [--clear-version-files] [--changelog PATH] [--changelog-copy PATH]… [--notes TEMPLATE] [--notes-listing PATH::AFTER::ENTRY]…` | what `prepare` commits onto `release/<V>` ([Preparing a release](../using/processes.md#preparing-a-release)); `\n` in MATCH and ENTRY is a newline; a PATH may be given more than once with different matches, each applied in order; with no flag, shows it |
| `kanbanr retro --sprint <SP-…>` | how a sprint went |

**Dependencies and scheduling**

| Command | What it does |
|---|---|
| `kanbanr ready` / `kanbanr blocked` | what can be started now, and what is waiting on something |
| `kanbanr ready --tasks [--lanes N] [--json]` | what can start now, task by task (FTR-060): **Running** (tasks in progress), **Ready** (dependencies Completed, item at its build stage, no file overlap with a running task; `*` marks the critical path, then its remaining chain in hours) and **Waiting**, one reason a line (waits on a task, writes a file a running task is writing, the item is not at its build stage, or no recorded files while another task of its item runs). `--lanes N` adds "Start together": up to N ready tasks that write no file in common, critical path first. Files in the config's `tasks.append_only` (default `CHANGELOG.md`) never conflict |
