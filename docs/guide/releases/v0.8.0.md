### DEF-034 — The Releases page lists releases in the order they were added, and a stage button has no confirmation

Releases listed newest first by version, a stage button that names the release and the stage and asks before it acts, and a command that steps a mistaken stage back while nothing is pushed or tagged, for the person promoting releases, so that a click lands on the release they mean and a wrong one is undone by a command, not by hand

- WHEN releases are listed (the Releases page, `kanbanr release list`, `kanbanr release list --json`, GET /projects/{p}/releases), THE SYSTEM SHALL order them newest first by version, with a pre-release before the release it precedes, and a version that does not parse after those that do, in the order they were added
- THE SYSTEM SHALL name the release and the stage in a promotion plan's `button` and so on every release button and in the sent-back steps: `Promote v0.6.0 to candidate`, `Cut v0.6.0`, `Confirm production: ship v0.6.0`, `Promote v0.6.0 to main again`, `Move v0.6.0 back to candidate`
- WHEN the person presses a release's button on a write-enabled monitor for a promotion that has no prepared record and no note to give, THE SYSTEM SHALL show the question `<button text>?` with a button of the same text and Cancel, SHALL act only on the second press, and SHALL change nothing on Cancel; a prepared record's confirmation (FTR-034) and a confirmation after the tag (FTR-026) keep their one labelled press
- WHEN `kanbanr release undo <V> --reason <why>` runs for a release that is not shipped or superseded, whose newest stage change is a promotion by a person, with no tag named `<V>` in the repository, no `move_main` or `tag` action on the stages that change entered, and the release branch on no remote, THE SYSTEM SHALL record a stage change back to the stage before it (or to no stage) that names the stage undone, delete the release branch only when every commit on it beyond its base is one kanbanr wrote (`Release <V>: …`) and it is checked out nowhere, and otherwise SHALL refuse and change nothing, naming why
- IF Claude runs `kanbanr release undo` or posts POST /projects/{p}/releases/{v}/undo, THEN THE SYSTEM SHALL refuse it as it refuses `release promote`, and the stage change an undo records SHALL carry its origin

- WHERE the monitor serves this board on localhost, THE SYSTEM SHALL answer a warm summary read in under 50 ms and a tab's slice in under 150 ms, and a page SHALL show something useful in under 300 ms
